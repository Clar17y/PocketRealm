# Security Audit: Quest & Shop System

## Files Reviewed
- `apps/api/src/routes/quests.ts` — GET quests, POST claim, POST reroll, POST bonus
- `apps/api/src/routes/shop.ts` — GET shop, POST purchase
- `apps/api/src/services/questService.ts` — getActiveQuests (lazy generation), incrementQuestProgress, claimQuestReward, claimDailyBonus, rerollQuest
- `apps/api/src/services/questShopService.ts` — getShopItems, purchaseItem, all applyEffect handlers (teleport, hearthstone, attribute reset, talent reset, bestiary tome, recipe scroll, contract reroll, buffs, prestige titles)

## Findings

### 1. Teleport Scroll Bypasses All Travel Restrictions
**Severity:** high
**Type:** business logic

**Description:** The `applyTeleport` function at `questShopService.ts:257-276` moves the player to any discovered zone without any of the normal travel checks: no HP check, no recovering check, no expedition lockout check, no over-encumbered check, and no travel turn cost. It also sets `lastTravelledFromZoneId` to the destination itself, giving the player a free breadcrumb return to wherever they teleport.

**Exploit Scenario:**
1. Player is in recovery state (knocked out) or at 0 HP.
2. Player purchases a teleport scroll.
3. The teleport bypasses `assertNotRecovering`, `assertCanAct`, and `checkExpeditionLockout`.
4. Player teleports to a town, avoiding the recovery turn cost entirely.
5. Since `lastTravelledFromZoneId = targetZoneId`, the player can breadcrumb-travel for free from their new location.

**Suggested Fix:** Add the standard pre-travel checks:
```ts
const hpState = await getHpState(playerId);
if (hpState.isRecovering) throw new AppError(400, 'Cannot teleport while recovering', 'IS_RECOVERING');
await checkExpeditionLockout(playerId);
```

### 2. Efficiency Reset Scroll Circumvents XP Window Design
**Severity:** medium
**Type:** business logic

**Description:** `applyEfficiencyReset` at `questShopService.ts:249-255` resets `dailyXpGained` to 0 for all skills. The XP efficiency/diminishing returns system (analyzed in the SKILL_CONSTANTS balance review) is designed to cap effective XP per window. This scroll allows players to reset the window mid-day, effectively doubling their XP earnings.

**Exploit Scenario:**
1. Player grinds until hitting the efficiency soft-cap (~67% of window capacity).
2. Player purchases an efficiency reset scroll (cost: quest tokens).
3. `dailyXpGained` resets to 0 — full efficiency restored.
4. Player grinds again, earning another 67% window capacity.
5. Total XP: ~134% of the designed cap per window.
6. If scroll is purchasable multiple times per day, the cap is effectively removed.

**Assessment:** The weekly purchase limit on the scroll (`weeklyLimit` field) may limit this. But if `weeklyLimit` is >= 7 (once per day), the cap is bypassed daily.

**Suggested Fix:** The scroll's design intent is to reset stale windows, not to double XP. Consider only allowing the reset when the window has expired or is close to expiry, not mid-window:
```ts
const skill = await tx.playerSkill.findFirst({ where: { playerId }, select: { lastXpResetAt: true } });
if (skill && !shouldResetWindowCap(skill.lastXpResetAt, now)) {
  throw new AppError(400, 'Efficiency window is still fresh', 'WINDOW_NOT_EXPIRED');
}
```

### 3. Quest Progress Is Not Atomic — Double Completion Possible
**Severity:** medium
**Type:** race condition

**Description:** `incrementQuestProgress` at `questService.ts:275-321` reads active quests, checks progress, and updates each quest individually without a transaction. Two concurrent progress increments (from combat + exploration happening near-simultaneously) could both read `currentValue: 9` and both update to `10`, with both triggering `completed: true`. This doesn't duplicate rewards (claiming is separate), but it creates duplicate completion notifications.

More importantly, the `currentValue` update at line 303 uses the value computed from the stale read (`quest.currentValue + amount`), not an atomic increment. If the read was stale, progress could be lost.

**Suggested Fix:** Use atomic increment within a transaction:
```ts
const updated = await prisma.playerQuest.update({
  where: { id: quest.id, status: 'active' },
  data: { currentValue: { increment: Math.min(amount, quest.targetValue - quest.currentValue) } },
});
```

### 4. Daily Bonus Check Has TOCTOU Race
**Severity:** low
**Type:** race condition

**Description:** `claimDailyBonus` at `questService.ts:360-407` checks `state.dailyBonusClaimed` outside the token update. Two concurrent bonus claims could both read `dailyBonusClaimed: false` and both proceed to award tokens. The update at line 398-404 sets `dailyBonusClaimed: true` without an optimistic lock.

**Exploit Scenario:**
1. Player sends two simultaneous `POST /quests/bonus` requests.
2. Both read `dailyBonusClaimed: false`.
3. Both count claimed dailies and pass.
4. Both increment tokens and set `dailyBonusClaimed: true`.
5. Player receives double daily bonus tokens.

**Suggested Fix:** Use `updateMany` with a guard:
```ts
const { count } = await prisma.playerQuestState.updateMany({
  where: { playerId, dailyBonusClaimed: false },
  data: { dailyBonusClaimed: true, questTokens: { increment: bonusTokens } },
});
if (count === 0) throw new AppError(400, 'Daily bonus already claimed', 'ALREADY_CLAIMED');
```

### 5. Quest Claim Doesn't Use Optimistic Lock
**Severity:** low
**Type:** race condition

**Description:** `claimQuestReward` at `questService.ts:327-354` uses a `$transaction` and reads the quest with `status: 'completed'`. The update at line 341 sets `status: 'claimed'` but without a WHERE guard. Two concurrent claims could both read `status: 'completed'` inside their transactions.

However, Prisma transactions with interactive queries (`$transaction(async fn)`) use READ COMMITTED isolation by default, which means the second transaction would see the first's committed changes. This is likely safe in PostgreSQL's default isolation, but the explicit optimistic lock pattern would be more defensive.

**Assessment:** Probably safe due to transaction isolation, but could be tightened.

### 6. Reroll Quest Is Well-Protected
**Severity:** info
**Type:** race condition

**Description:** `rerollQuest` at `questService.ts:428-507` correctly performs the reroll limit check INSIDE the transaction (line 477-479), preventing concurrent rerolls from exceeding the daily limit. This is a good implementation pattern.

**Assessment:** No issue — well-implemented guard.

### 7. Shop Purchase Is Well-Protected
**Severity:** info
**Type:** race condition

**Description:** `purchaseItem` at `questShopService.ts:78-152` performs all validation (token balance, weekly limit, lifetime limit, buff stacking) inside a `$transaction`. This prevents concurrent purchases from bypassing limits.

**Assessment:** No issue — solid transactional pattern.

### 8. Recipe Scroll Learns Random Recipe Without Skill Restriction for Advanced Recipes
**Severity:** low
**Type:** business logic

**Description:** `applyRecipeScroll` at `questShopService.ts:343-367` filters eligible recipes by `playerLevel >= requiredLevel` (line 356). It doesn't check whether the recipe is `isAdvanced` — it could learn an advanced/soulbound recipe that would normally only drop from a large encounter site boss clear. This bypasses the intended discovery mechanic.

**Assessment:** May be intentional — the scroll is a premium shop item. But it devalues the encounter site boss clear mechanic if advanced recipes can be bought.

---

### 9. Hearthstone Sets lastTravelledFromZoneId to homeTown
**Severity:** info
**Type:** business logic

**Description:** `applyHearthstone` at `questShopService.ts:278-293` sets `lastTravelledFromZoneId: player.homeTownId`. This means after using a hearthstone, the player can breadcrumb-travel BACK to their home town for free (they're already there). The breadcrumb destination matches the current zone, so breadcrumb travel would be blocked by the "already in this zone" check in the travel route.

**Assessment:** No issue — the `ALREADY_IN_ZONE` check prevents abuse.
