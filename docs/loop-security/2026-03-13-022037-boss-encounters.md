# Security Audit: Boss Encounter System

## Files Reviewed
- `apps/api/src/routes/boss.ts` — 6 boss route handlers (active, history, status, signup, round details)
- `apps/api/src/services/bossEncounterService.ts` — create, signup, round resolution, HP scaling, auto-signup, loot distribution trigger
- `apps/api/src/services/bossLootService.ts` — `distributeBossLoot`, `rollBossRecipeDrop`
- `apps/api/src/services/turnBankService.ts` — `spendPlayerTurnsTx` (referenced)
- `apps/api/src/services/hpService.ts` — `getHpState`, `setHp`, `enterRecoveringState` (referenced)
- `apps/api/src/services/equipmentService.ts` — `getEquipmentStats` (referenced)
- `apps/api/src/utils/routeHelpers.ts` — `assertNotRecovering`, `trackAchievements`, `calculateFleeWithGold`
- `apps/api/src/middleware/auth.ts` — JWT authentication

## Findings

### 1. Boss Round Resolution Is Not Concurrency-Safe
**Severity:** high
**Type:** race condition

**Description:** `checkAndResolveDueBossRounds` at `bossEncounterService.ts:636-649` queries all due encounters and resolves them sequentially. This function is called from multiple routes: `GET /boss/active` (line 35), `GET /boss/:id` (line 96), and `POST /boss/:id/signup` (line 147). If two players hit any of these endpoints simultaneously, two calls to `resolveBossRound` can execute concurrently for the same encounter.

The optimistic lock at line 431 (`updateMany WHERE roundNumber = encounter.roundNumber`) prevents double-writing the encounter row — the second call will get `updated.count === 0` and return null. However, before reaching that lock, significant side effects occur:
- All participant combat stats are fetched (lines 306-341)
- The boss round engine is resolved (line 383)
- HP scaling is applied and written (lines 298-301) — this write happens BEFORE the optimistic lock

The HP scaling write at line 298-301 is an unconditional `update` (not `updateMany` with a lock). Two concurrent resolutions will both rescale HP, potentially corrupting the boss's HP.

**Exploit Scenario:**
1. Boss round is due. Two players open the boss page simultaneously.
2. Both trigger `checkAndResolveDueBossRounds`.
3. Both read the encounter with `roundNumber: 3`.
4. Both rescale HP at line 298 — the second write may use stale `maxHp`/`currentHp`.
5. First resolution commits via optimistic lock. Second returns null.
6. But the HP scaling write from the second call persists, corrupting boss HP.

**Suggested Fix:** Move the HP scaling inside the optimistic lock check, or use a distributed lock (Redis `SET NX`) before resolving any boss round:
```ts
const lockKey = `boss_resolve:${encounterId}`;
const acquired = await redis.set(lockKey, '1', 'NX', 'EX', 30);
if (!acquired) return null;
try { ... } finally { await redis.del(lockKey); }
```

### 2. Boss Signup Doesn't Verify Player Is Alive (HP > 0)
**Severity:** medium
**Type:** business logic

**Description:** The signup route at `boss.ts:172` calls `assertNotRecovering(playerId)` which checks the recovering state but NOT whether the player has enough HP to participate. A player at 1 HP can sign up and enter a boss round. While `assertNotRecovering` passes the `hpState`, the signup at line 174 uses `hpState.maxHp` for the participant's `currentHp` — meaning the player enters the round at FULL HP regardless of their actual HP.

**Exploit Scenario:**
1. Player is at 1 HP from a previous combat.
2. Player signs up for boss round — pays turn cost, enters with `maxHp` (e.g., 500 HP).
3. Player effectively gets a free full heal by joining a boss fight.
4. Even if they die in the boss round, they've "healed" to full first and dealt damage.

**Suggested Fix:** Use the player's actual current HP instead of maxHp:
```ts
const participant = await signUpForBossRound(
  id, playerId, hpState.currentHp, // not maxHp
  body.autoSignUp ?? false,
);
```
Or require minimum HP threshold to sign up.

### 3. Round Details Expose All Participants' Combat Stats
**Severity:** medium
**Type:** data leakage

**Description:** `GET /boss/:id/round/:num` at `boss.ts:204-234` returns detailed combat statistics for ALL participants: `currentHp`, `currentStamina`, `currentMana`, `threat`, `damageAbsorbed`, `totalDamage`, `hits`, `crits`, and `status`. This is available to any authenticated player, not just participants.

**Exploit Scenario:**
1. Player A is not participating in a boss fight but wants to scout rival players.
2. Player A calls `GET /boss/<id>/round/1` to see exact HP, stamina, mana, and combat performance of all participants.
3. Uses this data to time PvP challenges when rivals are resource-depleted after a boss round.

**Suggested Fix:** Either restrict round details to participants only, or redact sensitive fields (currentHp, currentStamina, currentMana) for non-participants. Damage/healing leaderboard data can remain public.

### 4. Boss HP Scaling Creates Exploit With Single-Player Rounds
**Severity:** medium
**Type:** business logic

**Description:** At `bossEncounterService.ts:294-303`, boss HP is rescaled every round based on the number of participants: `scaledMaxHp = HP_PER_PLAYER * participantCount`, then `currentHp` is proportionally adjusted to preserve the HP percentage. This means if one round has 10 players and the next has 1 player, the boss HP drops by 90% while maintaining the same % remaining.

**Exploit Scenario:**
1. Round 1: 10 players sign up. Boss has 10,000 HP (1,000 per player). They deal 5,000 damage. Boss at 50%.
2. Round 2: Only 1 player signs up (others don't re-sign). Boss rescales to 1,000 max HP, 500 current HP (50% preserved).
3. Solo player easily finishes off 500 HP. Gets "top damage dealer" credit and potentially better loot share.

This can be coordinated: a guild signs up 10 members for round 1 to set up a high percentage, then only their strongest member signs up for round 2 to claim the kill.

**Suggested Fix:** Enforce a minimum HP floor based on the original `baseHp` (e.g., never rescale below 25% of baseHp), or only allow HP to scale UP (never down):
```ts
const scaledMaxHp = Math.max(encounter.baseHp, HP_PER_PLAYER * participantCount);
```

### 5. Auto-Signup Spends Turns Without Player Action
**Severity:** low
**Type:** business logic

**Description:** When `autoSignUp: true` is set (line 478-521), the system automatically creates next-round signups and spends turns for all auto-signed players. If a player enables auto-signup and then goes offline, the system will continue spending their turns each round until either the boss dies, they run out of turns (caught by try/catch at line 515), or they die in combat.

The try/catch at line 515-517 silently swallows all errors, including insufficient turns. The player gets no notification that they've been spending turns.

**Exploit Scenario:** Not a direct exploit, but a UX concern. A player enables auto-signup thinking it's for one round, then the boss fight lasts 20 rounds and they've spent 20 * `BOSS_SIGNUP_TURN_COST` turns without realizing it.

**Suggested Fix:** Add a maximum auto-signup round count (e.g., 5 rounds), or notify the player via a notification when auto-signup spends turns.

### 6. Loot Distribution Not Transactional — Partial Rewards Possible
**Severity:** medium
**Type:** race condition

**Description:** `distributeBossLoot` in `bossLootService.ts:67-178` iterates over all contributors, granting loot, XP, trophies, and recipes for each. None of this is wrapped in a transaction. If the server crashes midway through the loop, some players get rewards and others don't. The `rewardsByPlayer` data written to the encounter at line 608-611 would also not include the unprocessed players.

**Exploit Scenario:**
1. Boss is defeated with 8 contributors.
2. Loot distribution starts. Players 1-4 receive loot, XP, and trophies.
3. Server crashes during player 5's loot roll.
4. Players 5-8 receive nothing. The encounter's `rewardsByPlayer` field is never written.
5. Since the boss is already marked 'defeated' (line 437), the loot distribution won't re-run.

**Suggested Fix:** At minimum, wrap the entire distribution loop in a transaction. Or implement idempotent retry logic that checks which players have already received rewards before re-running.

### 7. Signup Route Triggers Round Resolution (User-Triggered Server Load)
**Severity:** low
**Type:** business logic

**Description:** Three routes call `checkAndResolveDueBossRounds(getIo())` as their first action: `GET /active` (line 35), `GET /:id` (line 96), and `POST /:id/signup` (line 147). This means every player browsing the boss page triggers round resolution for ALL due encounters. With many active bosses, this creates a user-triggered O(N) server operation.

**Exploit Scenario:** An attacker repeatedly polls `GET /boss/active` to force the server to check and resolve all due boss rounds, creating unnecessary load. While each round can only be resolved once (optimistic lock), the stat computation and engine resolution still execute fully before the lock check.

**Suggested Fix:** Move boss round resolution to a background timer only (it already exists in the server's interval at 60s). Remove `checkAndResolveDueBossRounds` from the route handlers.

### 8. Raid Wipe Flee Calculation Uses Stale Participant HP
**Severity:** low
**Type:** business logic

**Description:** When all players die (`result.allPlayersDead` at line 525), the flee/knockout calculation at lines 526-541 iterates over the `participants` array (built at line 306), not the `result.participantResults`. The `calculateFleeWithGold` call uses `p.maxHp` from the participant input, which is correct, but the progression state is re-fetched (line 528) rather than using the already-fetched data. More importantly, the actual post-combat HP state of the player is not considered — the flee calculation doesn't know the player was already at 0 HP from the boss fight.

**Assessment:** The implementation works correctly for the wipe scenario (all players are dead, so knockout/recovering state is appropriate). This is more of a code quality observation than a security issue.
