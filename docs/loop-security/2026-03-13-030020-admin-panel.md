# Security Audit: Admin Panel

## Files Reviewed
- `apps/api/src/routes/admin.ts` — 20+ admin endpoints (743 lines)
- `apps/api/src/middleware/admin.ts` — `requireAdmin` middleware
- `apps/api/src/middleware/auth.ts` — JWT authentication, role handling
- `apps/api/src/services/turnBankService.ts` — `refundPlayerTurns`
- `apps/api/src/services/inventoryService.ts` — `addStackableItem`
- `apps/api/src/services/worldEventService.ts` — `spawnWorldEvent`
- `apps/api/src/services/bossEncounterService.ts` — `createBossEncounter`

## Findings

### 1. All Admin Operations Target Only the Admin's Own Account
**Severity:** high
**Type:** business logic (design limitation)

**Description:** Every admin endpoint uses `req.player!.playerId` — the admin's own player ID. There is no way to target another player. For example:
- `POST /admin/turns/grant` grants turns to the admin, not a specified player
- `POST /admin/player/level` sets the admin's own level
- `POST /admin/items/grant` grants items to the admin
- `POST /admin/zones/teleport` teleports the admin
- `POST /admin/zones/discover-all` discovers zones for the admin

This means the admin panel cannot be used to help players, investigate issues, or perform moderation. An admin who wants to grant turns to a player must directly modify the database.

**Suggested Fix:** Add an optional `playerId` field to admin schemas that defaults to the requester's own ID:
```ts
const grantTurnsSchema = z.object({
  playerId: z.string().uuid().optional(),
  amount: z.number().int().min(1).max(1_000_000),
});
// Then: const targetId = body.playerId ?? req.player!.playerId;
```

### 2. Admin Role Check Uses JWT Claim, Not Database (Cross-reference with Auth Audit)
**Severity:** high
**Type:** privilege escalation

**Description:** As noted in the auth audit, `requireAdmin` at `admin.ts:5` checks `req.player?.role !== 'admin'` which reads the role from the JWT payload, not from the database. If an admin's role is revoked in the database, they retain admin access until their access token expires (15 minutes).

Combined with the hardcoded JWT secret fallback (also from the auth audit), this creates a chain: if `JWT_SECRET` is the default value, anyone can forge an admin token and use all admin endpoints.

**Suggested Fix:** Re-verify the role from the database for admin endpoints:
```ts
export async function requireAdmin(req, res, next) {
  const player = await prisma.player.findUnique({
    where: { id: req.player!.playerId },
    select: { role: true },
  });
  if (player?.role !== 'admin') throw new AppError(403, 'Admin access required', 'FORBIDDEN');
  next();
}
```

### 3. No Audit Logging for Admin Actions
**Severity:** medium
**Type:** business logic

**Description:** None of the admin endpoints create any audit trail. There are no activity logs, no system logs, and no record of what the admin did. The `createActivityLog` function used throughout the game is never called in admin routes. If an admin abuses their privileges (granting items, spawning events, modifying levels), there is no way to trace it.

**Suggested Fix:** Add audit logging to all mutating admin endpoints:
```ts
await createActivityLog({
  playerId: req.player!.playerId,
  activityType: 'admin_action',
  turnsSpent: 0,
  result: { action: 'grant_turns', targetPlayerId: playerId, amount },
});
```

### 4. Item Grant Has No Inventory Capacity Check
**Severity:** low
**Type:** business logic

**Description:** `POST /admin/items/grant` at line 180-213 creates items directly via `prisma.item.create` for non-stackable items, bypassing all inventory capacity checks. The admin can grant unlimited items, exceeding backpack capacity. For stackable items, `addStackableItem` is used which also has no capacity gate.

**Assessment:** As an admin action, bypassing capacity limits may be intentional. But it could accidentally put a player's account into an over-encumbered state that blocks normal gameplay.

**Suggested Fix:** Add an optional `skipCapacityCheck` flag that defaults to true for admin convenience, with a warning in the response when capacity is exceeded.

### 5. Bot Creation in Expedition Fill Creates Real Player Records
**Severity:** medium
**Type:** business logic

**Description:** `POST /admin/expedition/fill` at lines 643-731 creates real `Player` records with `isBot: true`, complete with guild memberships, turn banks, skills, combat templates, and items. These bot accounts:
- Count toward guild member limits
- Have real email addresses (`ExpBot_...@bot.local`)
- Have skills, items, and turn banks
- Are never cleaned up after the expedition

Over time, repeated use of this endpoint fills the database with abandoned bot players and inflates guild member counts.

**Suggested Fix:** Add a cleanup mechanism — either delete bot players after expeditions complete, or track them in a separate table. At minimum, exclude `isBot: true` from guild member count calculations.

### 6. Event Template Index Is User-Controlled Array Index
**Severity:** low
**Type:** input manipulation

**Description:** `POST /admin/events/spawn` at line 252 uses `WORLD_EVENT_TEMPLATES[templateIndex]` where `templateIndex` is user-controlled (validated as `z.number().int().min(0)` but with no `.max()`). If `templateIndex` exceeds the array length, the result is `undefined`, caught at line 253. This is safe but could be cleaner.

**Assessment:** No vulnerability — the undefined check prevents issues. But the schema should bound the index:
```ts
templateIndex: z.number().int().min(0).max(WORLD_EVENT_TEMPLATES.length - 1),
```

---

### 7. XP Grant Has No Upper Bound
**Severity:** low
**Type:** input manipulation

**Description:** `POST /admin/player/xp` at line 108 validates `amount: z.number().int().min(1)` with no max. An admin could grant billions of XP. The `characterLevelFromXp` function handles large values (returns max level), so this doesn't crash. But it creates irreversible character progression — there's no "remove XP" admin endpoint.

**Assessment:** Admin endpoint, so the operator is trusted. But adding a reasonable max (e.g., 10 million) prevents accidental typos.

---

### 8. Attribute Set Has No Total Validation
**Severity:** low
**Type:** business logic

**Description:** `POST /admin/player/attributes` at lines 131-153 allows setting individual attributes to any non-negative integer. There's no validation that the total attribute points spent doesn't exceed `attributePoints` available. An admin could set all attributes to 1000 without "spending" any points, creating a character with unlimited stats.

**Assessment:** Intentional for admin/testing use. But the response should clearly show the resulting total to prevent accidental over-allocation.

---

### 9. Event Cancel Doesn't Validate Event Status
**Severity:** info
**Type:** business logic

**Description:** `POST /admin/events/:id/cancel` at lines 321-332 sets any event to `expired` status regardless of its current status. An already-expired event can be "cancelled" again (no-op but wasteful). A completed event can be set back to expired. This is harmless but indicates missing status validation.
