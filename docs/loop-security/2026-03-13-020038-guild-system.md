# Security Audit: Guild System

## Files Reviewed
- `apps/api/src/routes/guild.ts` — all 24 guild route handlers
- `apps/api/src/services/guildService.ts` — create, read, settings, log, XP, role checks
- `apps/api/src/services/guildMembershipService.ts` — join, leave, kick, promote, demote, transfer, disband, join requests
- `apps/api/src/services/guildProjectService.ts` — start project, contribute turns/materials
- `apps/api/src/services/guildUpgradeService.ts` — activate upgrades, modifier calculation
- `apps/api/src/services/guildSpecializationService.ts` — select/respec specialization
- `apps/api/src/services/guildTaxService.ts` — tax calculation, treasury deposits
- `apps/api/src/middleware/auth.ts` — JWT authentication

## Findings

### 1. Guild Log Readable by Any Authenticated Player
**Severity:** medium
**Type:** data leakage

**Description:** The `GET /:id/log` route at `guild.ts:162` passes `req.params.id` directly to `getGuildLog(guildId, page)` without any membership or ownership check. Any authenticated player can read any guild's internal activity log by guessing/enumerating guild IDs.

**Exploit Scenario:**
1. Player A is not a member of Guild X.
2. Player A sends `GET /api/v1/guild/<guild-x-id>/log`.
3. The route calls `getGuildLog(guildId)` which simply queries `guildLog` by `guildId`.
4. Player A receives full log history: kicks, promotions, treasury spends, project activity, settings changes — all internal guild operations.

**Suggested Fix:** Add a membership check before returning logs:
```ts
const membership = await prisma.guildMember.findUnique({ where: { playerId } });
if (!membership || membership.guildId !== guildId) {
  throw new AppError(403, 'Not a member of this guild', 'NOT_IN_GUILD');
}
```

### 2. Guild Upgrades/Contracts/Projects Readable by Any Player
**Severity:** low
**Type:** data leakage

**Description:** The `GET /:id/upgrades` (line 171), `GET /:id/contracts` (line 189), `GET /:id/projects` (line 210), and `GET /:id/specialization` (line 248) routes all pass `req.params.id` directly to their service functions without verifying the requester is a guild member. Any authenticated player can enumerate another guild's active upgrades, contracts, project progress, and specialization.

**Exploit Scenario:**
1. Player A scouts a rival guild before PvP.
2. Sends `GET /api/v1/guild/<rival-id>/upgrades` to see their active combat/defense boosts.
3. Uses this intel to time PvP challenges when boosts are expired.

**Suggested Fix:** Add membership checks to these read endpoints, or accept this as public guild info by design. If intentional, document it.

### 3. Guild Creation: Turn Spend Outside Transaction Creates TOCTOU Window
**Severity:** medium
**Type:** race condition

**Description:** In `guildService.ts:153`, `spendPlayerTurns(playerId, CREATION_TURN_COST)` is called _before_ the `$transaction` block that creates the guild (line 155). Between turn deduction and guild creation, a concurrent request could also pass all checks (name not taken, not in a guild) and create a duplicate guild, or the guild creation could fail after turns are already spent.

**Exploit Scenario:**
1. Player sends two simultaneous `POST /api/v1/guild/` requests.
2. Both pass the "not already in a guild" check (line 144) and the "name not taken" check (line 147-150).
3. Both deduct turns at line 153.
4. Both enter the transaction — one succeeds, the other fails with a unique constraint violation on `guildMember.playerId`.
5. The failed request has already lost turns.

More critically: if both use different names, both could succeed creating two guilds, but the player ends up in only the last-committed one (unique constraint on `guildMember.playerId`), orphaning the other guild.

**Suggested Fix:** Move `spendPlayerTurns` inside the transaction using `spendPlayerTurnsTx(tx, ...)`, and move the membership/name-taken checks inside as well:
```ts
const guild = await prisma.$transaction(async (tx) => {
  const existing = await tx.guildMember.findUnique({ where: { playerId } });
  if (existing) throw new AppError(400, 'Already in a guild', 'ALREADY_IN_GUILD');
  await spendPlayerTurnsTx(tx, playerId, GUILD_CONSTANTS.CREATION_TURN_COST);
  return tx.guild.create({ ... });
});
```

### 4. `leaveGuild` Ignores Route `guildId` Parameter
**Severity:** low
**Type:** input manipulation

**Description:** The route `POST /:id/leave` at `guild.ts:104` passes `req.params.id` (the guild ID from the URL), but `leaveGuild(playerId)` at `guildMembershipService.ts:57` ignores it entirely — it only uses the player's actual membership to determine which guild to leave. This is safe (can't leave another guild), but creates a discrepancy where the URL guild ID is meaningless.

Similarly, `kickMember`, `promoteMember`, `demoteMember`, and `transferLeadership` all receive `req.params.id` in the URL but don't verify it matches the requester's actual guild — they use `requireRole(requesterId)` which returns the requester's guild membership regardless. The URL `guildId` is purely decorative.

**Exploit Scenario:** Not exploitable — the service layer correctly scopes all operations to the requester's actual guild. However, a user could construct confusing URLs like `POST /guild/<wrong-id>/kick` and it would still kick from their own guild, which is misleading.

**Suggested Fix:** Either validate `req.params.id` matches the membership guild, or remove it from the URL pattern. Validation is simpler:
```ts
if (requester.guildId !== guildId) throw new AppError(403, 'Not your guild', 'WRONG_GUILD');
```

### 5. `respondToJoinRequest` Doesn't Verify Request Belongs to URL Guild
**Severity:** medium
**Type:** privilege escalation

**Description:** At `guild.ts:122-125`, the route `POST /:id/requests/:requestId/accept` passes `req.params.requestId` to `respondToJoinRequest(playerId, requestId, accept)`. The service at line 156-158 queries `guildJoinRequest` filtering by `id: requestId` AND `guildId: membership.guildId`. This correctly scopes to the officer's own guild.

However, the `req.params.id` (guild ID from URL) is completely ignored. An officer could use a URL like `POST /guild/<other-guild-id>/requests/<their-own-request-id>/accept` and it would work because only `membership.guildId` matters. While not directly exploitable (the filter prevents cross-guild access), the URL guild ID should be validated.

**Suggested Fix:** Already safe due to the `guildId: membership.guildId` filter, but add an explicit check for consistency.

### 6. `disbandGuild` Cascade Deletes Without Member Notification
**Severity:** low
**Type:** business logic

**Description:** `disbandGuild` at `guildMembershipService.ts:297-302` simply does `prisma.guild.delete({ where: { id: guildId } })`. This presumably cascades to delete all `GuildMember`, `GuildProject`, `GuildUpgrade`, `GuildLog`, `GuildContract`, and `GuildJoinRequest` records. Members receive no notification — their guild simply vanishes.

**Exploit Scenario:**
1. Guild leader rage-quits and disbands the guild.
2. All members lose all project contributions (potentially thousands of donated turns and materials).
3. No confirmation, no cooldown, no refund mechanism.

**Suggested Fix:** Consider adding a cooldown or confirmation mechanism. At minimum, prevent disbanding while an active project exists. More robust: require a confirmation within a time window, or require all officers to approve.

### 7. Specialization Respec: Treasury Check Outside Transaction
**Severity:** low
**Type:** race condition

**Description:** In `guildSpecializationService.ts:93-100`, the treasury balance check (`guild.treasuryTurns < cost`) happens outside the `$transaction` block at line 105. However, the actual `decrement` happens inside the transaction. Two concurrent respec requests could both pass the check and then both decrement, potentially driving the treasury negative.

The transaction itself uses `{ decrement: cost }` which is an atomic SQL operation, so the treasury _will_ go negative rather than throw — PostgreSQL doesn't enforce `>= 0` constraints on integer columns by default.

**Exploit Scenario:**
1. Guild has exactly 10,000 treasury turns (equal to respec cost).
2. Leader sends two simultaneous respec requests to different paths.
3. Both pass the `guild.treasuryTurns < cost` check.
4. Both transactions execute `decrement: cost`.
5. Treasury ends at -10,000 turns.

**Suggested Fix:** Add a `WHERE treasuryTurns >= cost` guard inside the transaction using raw SQL or re-check after the update:
```ts
const result = await tx.guild.updateMany({
  where: { id: guildId, treasuryTurns: { gte: cost } },
  data: { specialization: newPath, treasuryTurns: { decrement: cost } },
});
if (result.count === 0) throw new AppError(400, 'Insufficient treasury', 'INSUFFICIENT_TREASURY');
```

### 8. Project Turn Contribution Has No Upper Bound Per Request
**Severity:** medium
**Type:** input manipulation

**Description:** The `contributeTurnsSchema` at `guild.ts:200` validates `amount: z.number().int().positive()` with no `.max()`. The service caps to the remaining goal (line 173: `Math.min(amount, remaining)`), but the per-project cap check at line 165 uses the player's cumulative total, not clamped.

If `PER_PROJECT_TURN_CAP` is, say, 50,000 and the project goal is 10,000, a player could send `amount: 50000`. The code would:
1. Pass the cap check (0 + 50000 <= 50000).
2. Clamp to `Math.min(50000, 10000) = 10000`.
3. Spend 10,000 turns and contribute them.

This is actually safe due to the clamping, but the cap check is evaluated _before_ clamping, meaning the cap comparison uses the unclamped `amount`. If `PER_PROJECT_TURN_CAP < project goal`, a player couldn't contribute up to the project goal because the cap check fires first with the unclamped value.

**Suggested Fix:** Apply clamping before the cap check, or validate against `effectiveAmount` instead of `amount`.

### 9. Material Contribution: No Upper Bound + Partial TOCTOU
**Severity:** medium
**Type:** race condition

**Description:** `contributeMaterials` at `guildProjectService.ts:206` reads the project's `materialsProgress` outside the transaction (line 262), calculates `remaining` and `effectiveQuantity`, then uses those values inside the transaction. Two concurrent material contributions could both see the same `currentProgress` and both contribute, exceeding the material goal.

**Exploit Scenario:**
1. Project needs 100 ore. Current progress: 90.
2. Player A and Player B both send `contributeMaterials` with quantity 20 simultaneously.
3. Both read `currentProgress = 90`, `remaining = 10`, `effectiveQuantity = 10`.
4. Both enter the transaction and update: `newProgress = 90 + 10 = 100`.
5. But since they read the stale value, the second write overwrites with `{ ore: 100 }` — Prisma JSON update replaces the whole object.
6. Net effect: both players lose 10 items each (20 total consumed), but only 10 counted toward the goal.

Actually, looking more closely, the materialsProgress update uses a hardcoded `newProgress` value (line 277) rather than an `increment`, so the second concurrent write would overwrite with `{ ore: 100 }` — which means progress is lost for one player, not exceeded. The player loses materials but gets no credit.

**Suggested Fix:** Move the `materialsProgress` read inside the transaction using `SELECT ... FOR UPDATE` semantics (Prisma interactive transactions already lock rows on update, but the read at line 222 is outside).
