# Security Audit: Zone Travel & HP/Rest System

## Files Reviewed
- `apps/api/src/routes/zones.ts` — GET zones, POST travel (689 lines)
- `apps/api/src/routes/hp.ts` — GET hp, POST rest, POST recover, GET rest/estimate
- `apps/api/src/services/hpService.ts` — `getHpState`, `rest`, `recover`, `setHp`, `enterRecoveringState`
- `apps/api/src/services/turnBankService.ts` — `spendPlayerTurns`, `spendPlayerTurnsTx`, `refundPlayerTurns` (referenced)
- `apps/api/src/services/guildTaxService.ts` — `applyGuildTax`, `getPlayerTaxRate`, `calculateInflatedCost` (referenced)
- `apps/api/src/services/zoneDiscoveryService.ts` — `getDiscoveredZoneIds`, `discoverZonesFromTown`, `respawnToHomeTown` (referenced)
- `apps/api/src/middleware/auth.ts` — JWT authentication

## Findings

### 1. Travel Turn Spend Is Not Atomic With Zone Update
**Severity:** high
**Type:** race condition

**Description:** The travel route at `zones.ts:288` calls `spendPlayerTurns(playerId, travelCost)` (non-transactional, standalone call) and then at line 289 calls `applyGuildTax(playerId, travelCost)` separately. The player zone update happens much later at line 656 (`prismaAny.player.update`). Between turn deduction and the zone update, a server crash or concurrent request means the player loses turns but doesn't move.

More critically, the entire ambush combat loop (lines 301-637) happens BETWEEN the turn spend and the zone update. If any ambush combat crashes, the player has paid turns but doesn't arrive.

Additionally, the `spendPlayerTurns` and `applyGuildTax` are two separate operations — not in the same transaction. The tax could fail after turns are already deducted.

**Exploit Scenario:**
1. Player initiates travel to a zone.
2. Turns are deducted at line 288.
3. Server crashes during ambush combat processing.
4. Player has lost turns but remains in the original zone.
5. On restart, the player can try again — double-paying for the same travel.

**Suggested Fix:** Wrap the turn spend, tax, and initial zone update in a single transaction. Process ambushes afterward, with the zone update already committed. If the player is knocked out during an ambush, the respawn logic already handles zone changes.

### 2. Breadcrumb Return Doesn't Validate Connection Exists
**Severity:** medium
**Type:** business logic

**Description:** At `zones.ts:235`, if `destinationId === player.lastTravelledFromZoneId`, the player gets free travel back. However, this check happens BEFORE the connection validation at line 210. The breadcrumb return at line 236 immediately updates the player's zone without checking whether a connection still exists between the current zone and the breadcrumb destination.

If zone connections are modified (admin removes a connection), a player can still breadcrumb-travel through the removed connection for free.

**Exploit Scenario:**
1. Player travels from zone A → zone B (sets lastTravelledFromZoneId = A).
2. Admin removes the A↔B connection.
3. Player breadcrumb-travels back to zone A for free — the connection check at line 210 is skipped.

**Suggested Fix:** Move the breadcrumb check AFTER the connection validation, or validate the connection exists for breadcrumb travel too.

### 3. Travel Refund Calculation Can Be Exploited
**Severity:** medium
**Type:** business logic

**Description:** When a player is defeated during a travel ambush, the refund at `zones.ts:507` is calculated as `travelCost - ambush.turnOccurred`. The `travelCost` includes guild tax inflation (line 287: `calculateInflatedCost(guildReducedCost, taxRate)`), but `ambush.turnOccurred` is a raw turn number (the turn during travel when the ambush happened).

If the player has a high tax rate and gets ambushed early, the refund could be larger than the base cost. For example: base cost 100, tax rate 20%, actual deduction 125. Ambush on turn 10. Refund = 125 - 10 = 115. But the base travel only costs 100, so the player effectively gains 15 turns.

**Exploit Scenario:**
1. Player is in a guild with 20% tax rate.
2. Player initiates travel (100 base cost → 125 after tax).
3. Player gets ambushed on turn 5 and is knocked out.
4. Refund = 125 - 5 = 120 turns. Player paid 125, got back 120, net cost 5.
5. But the guild still received the full tax deposit from line 289.
6. The refund comes from the turn bank directly, not from the guild treasury.
7. Over many trips, this creates a turn generation exploit: guild taxes go to treasury, refunds come from nowhere.

**Suggested Fix:** Calculate refund based on base cost, not tax-inflated cost:
```ts
const refundAmount = Math.max(0, guildReducedCost - ambush.turnOccurred);
```
Or refund the tax proportionally.

### 4. Rest Endpoint Has No Upper Bound on Turns
**Severity:** medium
**Type:** input manipulation

**Description:** The `restSchema` at `hp.ts:26` validates `turns: z.number().int().positive()` with no `.max()`. A player could send `turns: 999999999`. The `rest()` service at `hpService.ts:130-160` does handle this gracefully — it calculates effective turns after tax, computes healing, and only deducts the turns actually needed. The `calculateRestHealing` function caps healing at `maxHp - currentHp`.

However, `calculateInflatedCost(innerHealing.turnsUsed, taxRate)` at line 137 re-inflates the turns used. If `turnsUsed` is very small but `taxRate` is high, this could lead to spending more turns than the player intended, since they requested a large number but only needed a small amount of effective healing.

**Assessment:** The service correctly caps at needed healing, and only deducts the minimum turns. The tax inflation is correct behavior. This is a minor UX concern, not a vulnerability.

---

### 5. HP State Optimistic Locking Is Well-Implemented
**Severity:** info
**Type:** race condition

**Description:** Both `rest()` (hpService.ts:142-156) and `recover()` (hpService.ts:208-224) use `updateMany` with optimistic locking conditions (`WHERE currentHp = X AND lastHpRegenAt = Y AND isRecovering = Z`). If the HP state changes between the read and the update, `count !== 1` triggers a 409 error.

**Assessment:** This is a solid implementation. Concurrent rest requests will fail safely rather than double-healing. Good pattern.

---

### 6. Zone List Exposes All Zone IDs Including Undiscovered Ones
**Severity:** low
**Type:** data leakage

**Description:** The `GET /zones` endpoint at `zones.ts:121-149` returns ALL zones, including undiscovered ones. While undiscovered zones have `name: '???'` and no details, they still include the `id` field. A player can enumerate all zone UUIDs, which could be used in crafted requests to other endpoints (like the exploration issue from the previous audit where no zone presence check exists).

**Exploit Scenario:**
1. Player calls `GET /zones` and collects all zone IDs.
2. Player uses undiscovered zone IDs with `POST /exploration/start` (which lacks zone presence validation).
3. Player explores zones they haven't discovered yet.

**Suggested Fix:** Exclude zone IDs for undiscovered zones, or make them opaque (use hash/index instead of UUID). Better yet, fix the zone presence validation in exploration/combat (as recommended in the previous audit).

### 7. Travel Ambush Combat Doesn't Apply Guild Combat Modifiers
**Severity:** low
**Type:** business logic

**Description:** During travel ambush combat at `zones.ts:356-365`, `buildPlayerCombatStats` is called with the base progression and equipment stats, but `applyGuildCombatModifiers` is NOT called (unlike exploration/combat start which explicitly calls it). Guild combat damage and defense bonuses are missing from travel ambush fights.

The `guildMods` variable is fetched at line 280 for travel cost reduction but never applied to combat stats. This means travel ambushes are harder than regular combat for guild members who have combat upgrades active.

**Suggested Fix:** Add `applyGuildCombatModifiers(playerStats, guildMods)` after line 365:
```ts
const playerStats = buildPlayerCombatStats(...);
applyGuildCombatModifiers(playerStats, guildMods);
```

---

### 8. Breadcrumb Return Updates homeTownId Without Validation
**Severity:** low
**Type:** business logic

**Description:** At `zones.ts:246-249`, when breadcrumb-returning to a town, `homeTownId` is unconditionally set to the destination. This is correct behavior, but it happens outside any transaction and before the zone update. If the server crashes between the homeTownId update and the zone update, the player's home town changes but they don't move.

**Assessment:** Low impact — the player simply ends up with a different home town. Not exploitable.

---

### 9. Recovery Cost Can Be Zero Via Calculation
**Severity:** low
**Type:** business logic

**Description:** At `hpService.ts:192`, `recoveryCost` is `player.recoveryCost ?? 0`. If for any reason `recoveryCost` is null or 0 in the database, the player recovers for free. The `spendPlayerTurnsTx` call at line 206 would spend 0 turns. The `calculateRecoveryCost` function in game-engine should prevent this, but if the DB value is manually set to 0 or null, recovery is free.

**Suggested Fix:** Add a minimum cost floor:
```ts
const recoveryCost = Math.max(1, player.recoveryCost ?? 0);
```
