# Security Audit: Authentication System

## Files Reviewed
- `apps/api/src/routes/auth.ts` — register, login, refresh, logout endpoints
- `apps/api/src/middleware/auth.ts` — JWT generation/verification, authenticate middleware, token config
- `apps/api/src/middleware/admin.ts` — admin role check
- `apps/api/src/middleware/errorHandler.ts` — error response formatting
- `packages/database/prisma/schema.prisma` — Player and RefreshToken models

## Findings

### 1. JWT Secret Has Hardcoded Fallback
**Severity:** critical
**Type:** privilege escalation

**Description:** At `auth.ts:7`, the JWT secret is defined as:
```ts
const JWT_SECRET = process.env.JWT_SECRET || 'dev-secret-change-in-production';
```
If the `JWT_SECRET` environment variable is not set in production, the fallback `'dev-secret-change-in-production'` is used. This is a known, public string (committed to source code). Anyone who reads the source can forge arbitrary JWT tokens, including admin tokens.

**Exploit Scenario:**
1. Production deployment misconfigures or omits `JWT_SECRET`.
2. Attacker reads this source code and sees the fallback string.
3. Attacker crafts a JWT: `jwt.sign({ playerId: 'any-uuid', username: 'hacker', role: 'admin' }, 'dev-secret-change-in-production')`.
4. Attacker has full admin access to all endpoints.

**Suggested Fix:** Remove the fallback entirely and crash on startup if not set:
```ts
const JWT_SECRET = process.env.JWT_SECRET;
if (!JWT_SECRET || JWT_SECRET.length < 32) {
  throw new Error('JWT_SECRET must be set and at least 32 characters');
}
```

### 2. Role Embedded in JWT Is Trusted Without Re-Verification
**Severity:** high
**Type:** privilege escalation

**Description:** The `authenticate` middleware at `auth.ts:81` does `jwt.verify(token, JWT_SECRET) as AuthPayload` and trusts the `role` field from the token. The `requireAdmin` middleware at `admin.ts:5` checks `req.player?.role !== 'admin'` — which reads the role from the JWT, not from the database.

If a player's role is changed in the database (e.g., admin revoked), they retain admin access until their access token expires (15 minutes). More critically, if a player somehow obtains an admin-role JWT (see finding #1), there's no DB validation to catch it.

The refresh endpoint at `auth.ts:244-247` does re-read `player.role` from DB, which is good. But the access token carries the role for its entire 15-minute lifetime.

**Exploit Scenario:**
1. Admin user's role is revoked in the database (set to 'player').
2. Admin still has a valid access token with `role: 'admin'`.
3. For up to 15 minutes, the revoked admin retains full admin privileges.

**Suggested Fix:** For sensitive admin operations, re-verify the role from the database:
```ts
export async function requireAdmin(req, res, next) {
  const player = await prisma.player.findUnique({
    where: { id: req.player.playerId },
    select: { role: true },
  });
  if (player?.role !== 'admin') throw new AppError(403, ...);
  next();
}
```

### 3. Refresh Token Reuse Is Partially Allowed
**Severity:** medium
**Type:** business logic

**Description:** The refresh endpoint at `auth.ts:232-237` has an OR condition:
```ts
if (!storedTokenValid && !activeWithinWindow) {
  throw new AppError(401, ...);
}
```
This means a refresh succeeds if EITHER the stored token is valid OR the player was recently active. The `activeWithinWindow` check uses `lastActiveAt` from the player table.

After a refresh token is deleted at line 240, it's gone from the database. But if the player remains active (any authenticated request touches `lastActiveAt`), the old JWT-valid refresh token can still be used because:
1. `verifyRefreshToken` at line 215 only checks the JWT signature (not the DB).
2. `storedTokenValid` will be false (token deleted).
3. `activeWithinWindow` will be true (player recently active).
4. The OR condition passes.

This means a stolen refresh token remains usable for 24 hours after deletion, as long as the legitimate user stays active.

**Exploit Scenario:**
1. Attacker steals a refresh token.
2. Legitimate user refreshes, rotating to a new token. Old token is deleted from DB.
3. Attacker uses the old (deleted) refresh token.
4. JWT verification passes (signature valid, not expired).
5. `storedTokenValid` is false (deleted), but `activeWithinWindow` is true (user is playing).
6. Attacker gets a new access+refresh token pair.
7. Both attacker and legitimate user now have valid sessions.

**Suggested Fix:** Remove the `activeWithinWindow` bypass. Require the stored token to exist in the database:
```ts
if (!storedTokenValid) {
  throw new AppError(401, 'Invalid or expired refresh token', 'INVALID_TOKEN');
}
```
Or if the inactivity window is needed for UX, add an additional check that the token row exists (even if expired).

### 4. No Rate Limiting on Login Endpoint
**Severity:** medium
**Type:** input manipulation

**Description:** The `POST /auth/login` endpoint has no rate limiting. An attacker can make unlimited login attempts with different passwords to brute-force credentials. The bcrypt cost factor of 10 (line 56) provides ~100ms per attempt, allowing ~600 attempts/minute per attacker.

**Exploit Scenario:**
1. Attacker knows a user's email (from leaderboard or other data leakage).
2. Attacker sends thousands of login requests with common passwords.
3. No lockout, no delay, no CAPTCHA.
4. With a password list of 10,000 entries, the attack completes in ~17 minutes.

**Suggested Fix:** Add rate limiting per IP and per email:
```ts
// Example with express-rate-limit
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 10, // 10 attempts per 15 min per IP
  keyGenerator: (req) => req.ip,
});
authRouter.post('/login', loginLimiter, asyncHandler(...));
```
Also consider account lockout after N failed attempts.

### 5. Registration Race Condition: Duplicate Accounts
**Severity:** medium
**Type:** race condition

**Description:** At `auth.ts:42-53`, the registration endpoint checks for existing username/email, then creates the player. Between the check and the create, a concurrent registration with the same username/email could pass both checks. The database unique constraints on `username` and `email` will catch this (Prisma throws), but:
1. The turn spend at line 87 happens inside the `player.create`, so no turns are lost.
2. The error surfaces as an unhandled Prisma unique constraint error, which gets caught by the error handler as a 500 Internal Server Error — not a clean 409.

**Exploit Scenario:**
1. Two users simultaneously register with the same username.
2. Both pass the `findFirst` check (neither exists yet).
3. First create succeeds. Second throws a Prisma unique constraint error.
4. Second user sees a 500 error instead of a helpful "Username already taken" message.

**Suggested Fix:** Catch the Prisma unique constraint error and return a 409:
```ts
try {
  const player = await prisma.player.create({ ... });
} catch (err) {
  if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === 'P2002') {
    throw new AppError(409, 'Username or email already taken', 'USER_EXISTS');
  }
  throw err;
}
```

### 6. Registration Does Not Verify Email
**Severity:** low
**Type:** business logic

**Description:** Registration accepts any valid email format without verification. There is no email confirmation flow, no verification link, and no check that the email actually belongs to the registrant. This enables:
- Registering with someone else's email (potential harassment/impersonation)
- Registering with disposable/fake emails (spam accounts)
- No password recovery possible (no verified email to send reset to)

**Suggested Fix:** Either add email verification or remove email from registration entirely (username-only auth). For an MVP game, email verification may be unnecessary overhead.

### 7. Refresh Token Not Scoped — Any Player's Token Works for Any Player
**Severity:** low (mitigated)
**Type:** privilege escalation

**Description:** The refresh endpoint at `auth.ts:215-226` verifies the JWT, extracts `payload.playerId`, and then looks up both the stored token AND the player. However, the stored token lookup at line 219 uses `findUnique({ where: { token: refreshToken } })` without filtering by `playerId`. If an attacker could craft a JWT with a different `playerId` but the same token string (impossible due to JWT signing), they could refresh as another player.

**Assessment:** This is fully mitigated by JWT signing — the `playerId` in the token cannot be tampered with without invalidating the signature. The stored token lookup by token string (which is globally unique) is sufficient. Flagging as info-level since the defense is sound.

---

### 8. Logout Doesn't Require Authentication
**Severity:** info
**Type:** business logic

**Description:** The `POST /auth/logout` endpoint at `auth.ts:270-280` accepts any refresh token and deletes it without requiring an access token or verifying ownership. Anyone who knows a refresh token can invalidate it.

**Assessment:** This is standard practice — logout should be possible with just the refresh token. However, it means an attacker who intercepts a refresh token can perform a DoS by logging out the victim repeatedly. Since the victim can just log in again, this is low-impact.

---

### 9. No Password Complexity Beyond Length
**Severity:** low
**Type:** input manipulation

**Description:** The password schema at `auth.ts:23` validates `z.string().min(8).max(100)` — only length, no complexity requirements. Passwords like "12345678" or "password" are accepted.

**Suggested Fix:** Add basic complexity requirements or use a password strength library (zxcvbn). At minimum, consider requiring at least one letter and one number.

---

### 10. No Password Change or Reset Flow
**Severity:** info
**Type:** business logic

**Description:** There is no `POST /auth/change-password` or password reset endpoint. If a user forgets their password or suspects compromise, they have no way to change it without database intervention.

**Suggested Fix:** Add a `POST /auth/change-password` endpoint (requires current password + access token) for basic account security hygiene.
