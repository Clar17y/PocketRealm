# Security Audit: Crafting System (Craft, Forge, Salvage)

## Files Reviewed
- `apps/api/src/routes/crafting/craft.ts` — craft endpoint
- `apps/api/src/routes/crafting/forge.ts` — forge upgrade/reroll endpoints
- `apps/api/src/routes/crafting/salvage.ts` — salvage + batch salvage endpoints
- `apps/api/src/routes/crafting/helpers.ts` — shared schemas, validators, helpers
- `apps/api/src/routes/crafting/recipes.ts` — recipe listing endpoint
- `apps/api/src/utils/routeHelpers.ts` — `getOwnedItem`, `assertCanAct`, `assertNotRecovering`
- `apps/api/src/services/inventoryService.ts` — `consumeItemsByTemplateTx`, `getTotalQuantityByTemplate`, `addStackableItemTx`
- `apps/api/src/services/guildTaxService.ts` — `spendWithTaxTx`
- `apps/api/src/middleware/auth.ts` — JWT authentication

## Findings

### 1. Craft Quantity Has No Upper Bound
**Severity:** medium
**Type:** business logic

**Description:** The `craftSchema` validates quantity as `z.number().int().positive().default(1)` with no `.max()` bound. A player could submit `quantity: 1000000`, which would attempt to create 1 million items in a loop (line 198 of `craft.ts`), potentially causing server OOM or extreme DB load.

**Exploit Scenario:**
1. Player finds a non-stackable recipe they have materials for.
2. Sends `POST /api/v1/crafting/craft` with `{ recipeId: "...", quantity: 999999 }`.
3. The route enters a `for` loop creating 999,999 individual item rows, each with a `calculateCraftingCrit` + `rollBonusStatsForRarity` + `prisma.item.create` call.
4. Server hangs or runs out of memory. Even if materials are insufficient, the inventory check at line 104-109 uses `getTotalQuantityByTemplate` which runs _outside_ the transaction, so with enough materials the loop proceeds.

**Suggested Fix:** Add `.max(100)` (or similar) to the `craftSchema` quantity field:
```ts
quantity: z.number().int().positive().max(100).default(1),
```

### 2. TOCTOU Race Condition in Material Validation (Craft)
**Severity:** medium
**Type:** race condition

**Description:** The craft route checks material availability _outside_ the transaction (lines 104-109 call `getTotalQuantityByTemplate` which queries `prisma` directly), then consumes materials _inside_ the transaction (line 135 calls `consumeItemsByTemplateTx`). Between the check and the consumption, another concurrent request could consume the same materials.

However, this is partially mitigated because `consumeItemsByTemplateTx` will throw `INSUFFICIENT_ITEMS` if items aren't available inside the transaction. The real issue is that turns are already spent inside the transaction (line 132) before materials are consumed (line 135), so if material consumption fails, the transaction rolls back — which is correct behavior due to the `$transaction` wrapper.

**Exploit Scenario:**
1. Player has exactly 5 iron ore (needs 5 for a recipe).
2. Player sends two simultaneous craft requests.
3. Both pass the material check (both see 5 available).
4. First transaction succeeds, consuming 5 ore.
5. Second transaction's `consumeItemsByTemplateTx` throws, rolling back the turn spend too.

**Assessment:** The transaction rollback means no actual duplication occurs. The pre-check is optimistic and exists for UX (fast-fail before entering a transaction). This is low-severity — the race only causes a confusing error message, not an exploit.

**Suggested Fix:** No urgent fix needed. The transaction integrity holds. Optionally, move material checks inside the transaction for consistency.

### 3. Forge Upgrade Success Check Happens After Turn/Sacrifice Consumption
**Severity:** low
**Type:** business logic

**Description:** In `forge.ts` upgrade (lines 72-85), turns are spent and the sacrificial item is deleted inside a transaction. Then _after_ the transaction commits, the success chance is calculated and the random roll happens (lines 86-103). This means if the server crashes between the transaction commit and the item update on success, the player loses their turns + sacrifice but gets no upgrade.

Additionally, `successChance` is checked for `null` at line 88 _after_ the sacrifice has already been consumed. If `calculateForgeUpgradeSuccessChance` returns `null` (legendary item), the sacrifice and turns are already gone.

**Exploit Scenario:** Not player-exploitable, but a server crash at the wrong moment means lost resources. The legendary check at line 88 is a defense-in-depth issue — the earlier check at line 57-59 should catch it, but they use different functions (`getNextRarity` vs `calculateForgeUpgradeSuccessChance`).

**Suggested Fix:** Move the `successChance` calculation and null-check before the transaction, alongside the `getNextRarity` check. The random roll should also ideally be generated before the transaction, with item mutation happening atomically.

### 4. Activity Log Leaks Internal RNG Values
**Severity:** low
**Type:** data leakage

**Description:** The forge upgrade activity log (lines 144-169 and 213-236) records `successChance`, `adjustedChance`, and `roll` (the raw `Math.random()` value). The craft endpoint response also includes `craftedItemDetails` with full bonus stat breakdowns. While activity logs are per-player, if any endpoint exposes another player's activity logs, these internal values reveal the exact RNG mechanics.

**Exploit Scenario:**
1. If activity logs are ever shared (guild logs, public profiles), players can reverse-engineer exact success rates and confirm whether forge luck buffs are working correctly.
2. The `roll` value in the JSON response (line 187) is sent directly to the client, letting players build statistical models of the RNG.

**Suggested Fix:** Don't include `roll` in the client response. Keep it in the activity log for debugging but strip it from `res.json()`. Consider removing `adjustedChance` from responses too — only show `success: true/false`.

### 5. Batch Salvage Doesn't Validate Duplicate Item IDs
**Severity:** low
**Type:** input manipulation

**Description:** The `salvageBatchSchema` validates `itemIds: z.array(z.string().uuid()).min(1).max(50)` but doesn't enforce uniqueness. A player could submit the same item ID multiple times: `{ itemIds: ["abc", "abc", "abc"] }`.

**Exploit Scenario:**
1. Player sends `POST /api/v1/crafting/salvage/batch` with `{ itemIds: ["item-1", "item-1", "item-1"] }`.
2. `prismaAny.item.findMany` with `id: { in: body.itemIds }` deduplicates via SQL `IN`, so only 1 item is returned.
3. However, if `findMany` didn't deduplicate, the item could appear in `plans` multiple times.
4. In practice, `prisma.item.deleteMany` at line 269 would delete the item once, and `deleted.count` (1) wouldn't match `plans.length` (3), causing a 409 error.

**Assessment:** Not exploitable due to Prisma's `IN` deduplication and the delete count check. But the inconsistency between input array length and processing length could cause confusing errors.

**Suggested Fix:** Add `.transform(ids => [...new Set(ids)])` or use Zod's `.refine()` to reject duplicates:
```ts
itemIds: z.array(z.string().uuid()).min(1).max(CRAFTING_CONSTANTS.SALVAGE_BATCH_LIMIT)
  .refine(ids => new Set(ids).size === ids.length, 'Duplicate item IDs'),
```

### 6. Recipes Endpoint Exposes All Recipes (No Skill Level Filter)
**Severity:** info
**Type:** data leakage

**Description:** `GET /api/v1/crafting/recipes` fetches _all_ recipes from the database and returns them to the client (line 41-67 in `recipes.ts`). While advanced recipes show a `discoveryHint` instead of full details when not unlocked, all standard recipes are visible regardless of skill level — including their materials, turn costs, and XP rewards.

**Exploit Scenario:** A new player can see every recipe in the game, including high-level ones, and plan optimal progression paths. This may or may not be intended design.

**Assessment:** Likely intentional for UX (showing what's craftable at higher levels motivates progression). Flagging as informational.

---

### 7. Craft Route Creates Items Outside Transaction
**Severity:** medium
**Type:** race condition

**Description:** The craft route's transaction (lines 131-139) only covers turn spending and material consumption. Item creation (lines 158-243) happens _after_ the transaction commits, outside any transaction. If item creation fails partway through (e.g., DB error on iteration 5 of 10), the player has already lost turns and materials but received only some items.

**Exploit Scenario:**
1. Player crafts `quantity: 10` of a non-stackable item.
2. Transaction succeeds: turns spent, materials consumed.
3. Item creation loop starts. Items 1-4 created successfully.
4. DB connection drops or constraint violation on item 5.
5. Player loses all turns + materials, gets only 4 of 10 items.

**Suggested Fix:** Move item creation inside the transaction, or wrap the entire operation (turn spend + material consume + item create) in a single transaction. The current split creates a partial-failure window.
