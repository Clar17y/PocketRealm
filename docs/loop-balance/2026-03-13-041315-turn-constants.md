## Analysis

### Regeneration Curve

Turn regeneration is perfectly linear: `turns(t) = min(storedTurns + t, BANK_CAP)` where t is elapsed seconds.

- Per minute: 60 turns
- Per hour: 3,600 turns
- Per day: 86,400 turns (but capped at 64,800)
- Time to fill from 0: 64,800 seconds = 18 hours exactly

The system uses lazy calculation -- turns are not ticked by a cron. On each request, the service computes `floor((now - lastRegenAt) / 1000) * REGEN_RATE` and adds it to the stored balance, then clamps to `BANK_CAP`. This is mathematically clean (no drift, no rounding accumulation) because REGEN_RATE is exactly 1.

### Theoretical Daily Turn Budget

A player generates 86,400 turns/day (1/sec * 86,400 sec/day) but can only store 64,800. The overflow loss depends on play pattern:

- **Optimal player** (plays exactly when cap is reached every 18h): Uses all 86,400 turns/day.
- **Once-daily player** (plays once per 24h): Banks 64,800, wastes 21,600 (25% loss).
- **Twice-daily player** (plays every 12h): Banks 43,200 per session, uses all 86,400/day (no waste if spending below cap before logging off).
- **Sleep pattern** (8h sleep, active 16h): At most wastes `max(0, 8*3600 - 64800 + preLogoff_balance)`. If they drain to 0 before sleeping, they wake with 28,800 and waste nothing.

The 18-hour cap is generous -- it means a player who logs in at the same time each day only wastes `(24 - 18) * 3600 = 21,600` turns, which is 25% of daily production. This is a standard anti-hoarding mechanism.

### Turn Budget vs Activity Costs

With a daily budget of ~64,800–86,400 turns, let's compute how many actions a player can perform:

| Activity | Cost | Actions per day (64.8k budget) |
|---|---|---|
| Combat encounters | 50 | 1,296 |
| Exploration (100 turns) | 100 | 648 |
| Exploration (1000 turns) | 1,000 | 64 |
| Gathering | 30 | 2,160 |
| Crafting | 50 | 1,296 |
| Zone travel | 100 | 648 |
| PvP challenges | 500 | 129 |
| Forge upgrades (common) | 100 | 648 |
| Forge upgrades (epic) | 1,000 | 64 |

A typical gameplay session might involve:
1. Travel to zone: 100 turns
2. Explore (500 turns avg): 500 turns
3. Fight encounter: 50 turns
4. Repeat explore+fight 10x: 5,500 turns
5. Gather a few nodes: 90 turns
6. Travel back to town: 100 turns (free via breadcrumb)
7. Craft 2 items: 100 turns
8. Repair: 100 turns

Total ~6,440 turns for a moderate play session. A daily player with 64,800 turns can run ~10 of these "loops", which seems about right for an idle/async game.

### STARTING_TURNS = BANK_CAP Interaction

New players get 64,800 turns (= BANK_CAP). Since they start at full cap, every second that passes before their first login is wasted. This is standard practice, but it creates an interesting new-player UX issue:

- A player who registers but doesn't play for 3 days still has 64,800 turns (not 64,800 + 259,200). This is correct and intended -- the cap prevents idle stockpiling.
- But a player who registers and immediately starts playing has the same 64,800 turns as someone who waits a week. No penalty for delayed start.

### Bank Cap Breakpoint Analysis

The 64,800 cap creates critical breakpoints for expensive activities:

- **Respec (50,000 turns):** Requires 77% of a full bank. A player must save up ~13.9 hours of regen without spending. This is achievable but punishing -- it requires discipline.
- **Guild creation (50,000 turns):** Same as respec. Players at endgame who routinely spend turns on combat/crafting need to consciously save up.
- **Full exploration (10,000 turns):** Requires 15.4% of bank. Easy to afford multiple times.

The gap between "most expensive routine activity" (PvP challenge: 500) and "most expensive one-time activity" (respec/guild: 50,000) is 100x. This is a very large spread. The one-time costs exist to create meaningful gating, but 50,000 turns is not actually difficult if you simply wait 13.9 hours.

### Clock Manipulation Vulnerability

The lazy calculation model is `turns = stored + floor((now - lastRegenAt) / 1000)`. The `now` parameter is always `new Date()` on the server, so client clock manipulation is irrelevant. The system is safe against this attack vector.

However, the optimistic concurrency control (OCC) pattern in `turnBankService.ts` uses `updateMany` with a WHERE clause matching both `currentTurns` and `lastRegenAt`. If two requests arrive simultaneously:
1. Both read the same (currentTurns=1000, lastRegenAt=T1)
2. Both compute a new balance
3. First update succeeds, changes lastRegenAt to T2
4. Second update WHERE fails (lastRegenAt no longer matches T1)
5. Retry loop (max 3 attempts)

This is correct. The 3-attempt limit is sufficient for normal play patterns. A player would need to issue 4+ simultaneous requests to exhaust retries, which would require scripted abuse.

### Guild Tax Amplification

When a player is in a guild with a tax rate, the actual turns deducted from the bank are *inflated* to cover the tax. The formula is:

```
actualCost = ceil(baseCost / (1 - taxRate/100))
```

At maximum tax (20%): `actualCost = ceil(baseCost / 0.8) = ceil(1.25 * baseCost)`

This means a 20% guild tax makes every turn-based activity 25% more expensive. Over a full daily budget:
- Without tax: 64,800 effective turns
- With 20% tax: 64,800 * 0.8 = 51,840 effective turns (12,960 to treasury)

This is a significant hidden cost. A player in a max-tax guild generates 20% fewer effective turns per day. The tax system is transparent (called out in the UI), but the compounding effect on expensive activities is notable:
- PvP challenge: 500 → 625 actual turns
- Forge upgrade (epic): 1,000 → 1,250 actual turns
- Respec: 50,000 → 62,500 actual turns (which is **96.5% of the bank cap**)

## Issues Found

### 1. Respec Under Max Guild Tax Is Nearly Impossible From Cap

With 20% guild tax, respec costs `ceil(50000 / 0.8) = 62,500` turns. The bank cap is 64,800. This means a player must have 96.5% of a full bank to respec while in a max-tax guild. They'd need to save for 17.36 hours without spending any turns. While technically possible, it forces a choice: leave the guild, or save very carefully. This may be intentional design friction, but it's worth flagging.

### 2. Overnight Turn Waste is Non-Trivial

A player who plays once in the morning and once in the evening (12h gap) wastes nothing. But a player who plays only once per day (24h gap) wastes 21,600 turns (25%) to the cap. The 18h cap rewards splitting play into two sessions but doesn't severely punish once-daily players. However, the gap between "optimal" (0% waste) and "once-daily" (25% waste) is large enough to create a felt advantage for more active players in an ostensibly async game.

### 3. Starting Turns Equals Bank Cap — No Urgency Buffer

Setting STARTING_TURNS = BANK_CAP means new players start wasting turns immediately if they don't play right after registration. Consider that a new player who registers at night and plays the next morning has already wasted hours of regen. An alternative would be STARTING_TURNS < BANK_CAP (e.g., 43,200 = 12h) so the player has a buffer before hitting cap. The tradeoff: less generous first impression vs. less waste. Current design is fine for player friendliness.

### 4. No Turn Sink for High-Activity Endgame

The most expensive *repeatable* activity is PvP challenge at 500 turns. A player can do 129 PvP fights per day. Combat encounters cost only 50 turns (1,296/day). For an endgame player who has completed zone exploration and crafted their gear, turns accumulate faster than they can be spent in meaningful ways. The game may need additional endgame turn sinks (expeditions at 300 partially fill this role, but are group-gated).

### 5. REGEN_RATE = 1 Makes Balancing Trivial But Inflexible

With REGEN_RATE fixed at 1 turn/second, all turn costs are effectively measured in seconds of real time. This is elegant for reasoning (50-turn combat = 50 seconds of regen) but means the only balance lever is cost-per-action. If the game ever needs to speed up progression globally, there's no multiplier to tweak without changing every cost constant. The premium subscription design doc already identifies this — it proposes a 1.1x regen rate for subscribers.

## Recommendations

### Keep Current Values (No Changes Needed)

The current TURN_CONSTANTS are well-calibrated:

1. **REGEN_RATE = 1** is clean, simple, and makes all turn costs human-readable as seconds. Do not change.

2. **BANK_CAP = 64,800 (18h)** is a solid choice. It's generous enough for once-daily players (75% efficiency) while still encouraging regular engagement. The standard range for idle games is 12–24 hours; 18h is squarely in the sweet spot.

3. **STARTING_TURNS = 64,800** is player-friendly. The waste issue is minimal — new players are excited and tend to play immediately.

### Consider for Future Iteration

| Change | Rationale | Risk |
|---|---|---|
| Add a weekly "turn overflow" reward (e.g., 10,000 bonus turns for 7-day login streak) | Rewards consistent players without penalizing casuals | Low — purely additive |
| Exempt one-time costs (respec, guild creation) from guild tax | Prevents the 96.5% bank requirement edge case | Low — minor guild treasury reduction |
| Add endgame repeatable turn sinks (e.g., dungeon keys, cosmetic crafting) | Prevents turn rot for capped players | Medium — needs content design |
| Increase BANK_CAP to 72,000 (20h) | Reduces once-daily waste from 25% to 17% | Low — slightly less engagement pressure |

## Risk Level

low — The turn economy is fundamentally sound. The linear regen model with lazy calculation is correct, race-condition-safe (via OCC), and resistant to clock manipulation. The cap is well-sized for the activity cost structure. The only concerns are edge cases (respec under guild tax) and endgame turn velocity, neither of which requires immediate action.
