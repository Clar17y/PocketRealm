# Database Audit: hpService

**Date:** 2026-03-14
**Service:** `apps/api/src/services/hpService.ts` (264 lines, 5 exported functions + 1 private)

## Prisma Models Touched

Direct: `Player`
Via sub-services: `PlayerEquipment`, `Item`, `ItemTemplate` (via `getEquipmentStats`), `TurnBank`, `GuildMember`, `Guild` (via tax)

---

## Findings

### N+1 Queries

**1. Two `player.findUnique` calls for the same player in every read function**

`getHpState`, `rest`, and `recover` all follow the same pattern: first query fetches HP fields, then `getVitalityLevel` issues a second query for `attributes`. Both hit the Player table by PK.

```ts
// Query 1: HP fields
const player = await prisma.player.findUnique({
  where: { id: playerId },
  select: { currentHp: true, lastHpRegenAt: true, isRecovering: true, recoveryCost: true },
});

// Query 2: attributes (inside getVitalityLevel)
const player2 = await prisma.player.findUnique({
  where: { id: playerId },
  select: { attributes: true },
});
```

This is 2 round-trips for data that could be fetched in 1 query by adding `attributes: true` to the first select.

**Impact:** Every call to `getHpState` costs 2 player queries + 1 equipment query. Since `getHpState` is used as a gate check for combat, PvP, scouting, exploration, and rest, this doubles the player-fetch cost across most game actions.

### Missing Indexes

No issues — all queries use Player PK lookups.

### Payload Bloat

**1. `getEquipmentStats` called for a single number (lines 48, 104, 193)**
All three read functions call `getEquipmentStats(playerId)` which fetches all equipped items with full `include: { item: { include: { template: true } } }`. Only `equipmentStats.health` is used (for `calculateMaxHp`).

```ts
const equipmentStats = await getEquipmentStats(playerId);
const maxHp = calculateMaxHp({
  vitalityLevel,
  equipmentHealthBonus: equipmentStats.health,  // only field used
});
```

### Cache Issues

**No Redis usage.**

| Function | Call Frequency | Data Volatility | Cache Candidate? |
|----------|---------------|----------------|-----------------|
| `getHpState` | Every combat/PvP/explore action (gate check) | HP regens passively, changes on damage | Moderate — short TTL with combat invalidation |
| `getEquipmentStats` (via health bonus) | Same as getHpState | Only on equip/unequip | **Strong** — equipment health bonus rarely changes |

The equipment health bonus is the strongest cache candidate — it's a single integer that only changes on equip/unequip, but gets fetched (with full equipment + template data) on every HP check.

### Migration Risks

None specific to this service. The `updateMany` with optimistic concurrency (checking `currentHp`, `lastHpRegenAt`, `isRecovering`) is a solid pattern for preventing race conditions.

## Query Patterns

### `getHpState` — 3 queries

| Step | Query | Select/Include | Index |
|------|-------|---------------|-------|
| 1 | `player.findUnique` | `select: { currentHp, lastHpRegenAt, isRecovering, recoveryCost }` | PK |
| 2 | `player.findUnique` (via `getVitalityLevel`) | `select: { attributes }` | PK |
| 3 | `getEquipmentStats` | `include: { item: { include: { template: true } } }` | `@@id([playerId, slot])` |

### `rest` — 6–7 queries

| Step | Query | Notes |
|------|-------|-------|
| 1 | `player.findUnique` (HP state) | PK |
| 2 | `player.findUnique` (vitality) | PK — duplicate |
| 3 | `getEquipmentStats` | Full equipment fetch |
| 4 | `getPlayerTaxRateTx` (in tx) | GuildMember + Guild |
| 5 | `spendPlayerTurnsTx` (in tx) | TurnBank |
| 6 | `applyGuildTaxTx` (in tx) | Guild update |
| 7 | `player.updateMany` (in tx) | Optimistic update |

### `recover` — 5–6 queries

Same as `rest` without tax: player HP state + vitality + equipment + turn spend + player update.

### `setHp` / `enterRecoveringState` — 1 query each

Simple `player.update` by PK. Clean.

## Suggested Fixes

### Priority 1 — Merge player queries

Combine the HP state and vitality fetches into a single query:

```ts
const player = await prisma.player.findUnique({
  where: { id: playerId },
  select: {
    currentHp: true,
    lastHpRegenAt: true,
    isRecovering: true,
    recoveryCost: true,
    attributes: true,        // ← add this
  },
});
const vitalityLevel = normalizePlayerAttributes(player.attributes).vitality;
```

Saves 1 query per `getHpState`/`rest`/`recover` call. Since `getHpState` is a gate for most game actions, this has wide impact.

### Priority 2 — Cache equipment health bonus

The full `getEquipmentStats` call fetches all equipment + templates to produce stat totals. For HP calculation, only `health` is needed. Options:

**a)** Cache the full `EquipmentStats` result in Redis (keyed by playerId, invalidated on equip/unequip). Benefits all consumers, not just hpService.

**b)** If caching is too complex, at minimum pass pre-fetched equipment stats into `getHpState` when the caller already has them (e.g., in `preparePlayerForCombat`).

### Priority 3 — Accept preloaded data

Add an optional `preloaded` parameter to `getHpState`:

```ts
export async function getHpState(
  playerId: string,
  now?: Date,
  preloaded?: { attributes?: Json; equipmentHealth?: number },
): Promise<HpState> {
```

This lets callers like `preparePlayerForCombat` and `buildPvpCombatant` pass data they've already fetched, avoiding the 2 extra queries.
