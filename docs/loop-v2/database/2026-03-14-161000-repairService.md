# Database Audit: repairService

**Date:** 2026-03-14
**Service:** `apps/api/src/services/repairService.ts` (121 lines, 3 exported functions)

## Prisma Models Touched

Direct: `PlayerEquipment`, `Item`, `ItemTemplate`
Via sub-service: `TurnBank` (via `spendPlayerTurnsTx`)

---

## Findings

### N+1 Queries

**1. `repairAllEquipped` — per-item repair loop (lines 101–117)**
Loops over damaged items calling `repairItemDurability` individually. Each call does 1 `item.updateMany` with optimistic concurrency.

```ts
for (const ic of itemCosts) {
  const { newMax, decay } = await repairItemDurability(tx, { ...ic.item, ownerId: playerId }, randomFn);
  repairedItems.push({ ... });
}
```

For 5 damaged items: 5 sequential `updateMany` calls. Each item gets a different random `decay` value, making a single `updateMany` impossible without raw SQL.

**Impact:** Moderate — repair is a player-initiated action (not hot-path like combat). Typical case is 1–6 items.

### Missing Indexes

No issues. All queries use `@@id([playerId, slot])` on `PlayerEquipment` and PK on `Item`.

### Payload Bloat

**1. Equipment fetch with full includes (lines 68–71)**
Same `include: { item: { include: { template: true } } }` pattern. Uses only: `item.id`, `item.currentDurability`, `item.maxDurability`, `item.ownerId` (implicit), `template.maxDurability`, `template.itemType`, `template.name`.

```ts
tx.playerEquipment.findMany({
  where: { playerId, itemId: { not: null } },
  include: { item: { include: { template: true } } },
});
```

### Cache Issues

No Redis usage. The equipment fetch runs inside a `$transaction`, so caching within the tx isn't applicable. No external cache candidates since repair is an infrequent player-initiated action.

### Migration Risks

None. Good use of optimistic concurrency (`updateMany` with state check + count assertion).

## Query Patterns

### `repairItemDurability` — 1 query (called within tx)

| Query | Details | Index |
|-------|---------|-------|
| `item.updateMany({ id, ownerId, currentDurability, maxDurability })` | Optimistic concurrency update | PK (id) |

### `repairAllEquipped` — 2 + N queries

| Step | Query | Notes |
|------|-------|-------|
| 1 | `playerEquipment.findMany` with full includes | Equipment fetch |
| 2 | `spendPlayerTurnsTx` | Turn deduction (1–2 queries) |
| 3–N | `repairItemDurability` per damaged item | 1 update each |

**Typical total:** 2 + 1–6 = **3–8 queries per repair action**

## Suggested Fixes

### Priority 1 — Slim the equipment query

```ts
tx.playerEquipment.findMany({
  where: { playerId, itemId: { not: null } },
  select: {
    slot: true,
    item: {
      select: {
        id: true,
        ownerId: true,
        currentDurability: true,
        maxDurability: true,
        template: { select: { maxDurability: true, itemType: true, name: true } },
      },
    },
  },
});
```

### Priority 2 — Batch repair with raw SQL (optional)

Since each item gets a random `decay`, batch only if acceptable to compute decay in JS and apply via raw SQL:

```ts
const updates = itemCosts.map(ic => {
  const decay = computeDecay(randomFn);
  const newMax = Math.max(MIN, (ic.item.maxDurability ?? ic.item.template.maxDurability) - decay);
  return { id: ic.item.id, newMax, decay };
});

await tx.$executeRaw`
  UPDATE items SET current_durability = v.new_max, max_durability = v.new_max
  FROM (VALUES ${Prisma.join(updates.map(u => Prisma.sql`(${u.id}::uuid, ${u.newMax})`))} ) AS v(id, new_max)
  WHERE items.id = v.id
`;
```

Reduces N updates to 1. Trade-off: loses optimistic concurrency per-item (acceptable for a player-initiated action within a tx).
