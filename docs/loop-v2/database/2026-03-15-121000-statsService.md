## Findings

### N+1 Queries

**None.** This service is an exemplar of batching — uses single raw SQL queries with correlated subqueries instead of N individual queries. `resolveAllStats` resolves 12 derived stats + guild stats in just 3 parallel queries (1 mega raw SQL + 1 Prisma + 1 guild raw SQL).

### Missing Indexes

**1. `BossParticipant` — no `@@index([playerId])` for stats queries**
The raw SQL queries filter `boss_participants` by `player_id`:

```sql
-- In resolveAllStats:
SELECT COUNT(DISTINCT bp.encounter_id)::int
FROM boss_participants bp
JOIN boss_encounters be ON be.id = bp.encounter_id
WHERE bp.player_id = ${playerId} AND be.status = 'defeated'

SELECT SUM(total_damage)::int FROM boss_participants WHERE player_id = ${playerId}
```

`BossParticipant` has `@@unique([encounterId, playerId, roundNumber])` and `@@index([encounterId, roundNumber])` — both have `encounterId` as the leading column. A `player_id`-only filter requires a full table scan.

**All other tables are well-indexed:**
- `PlayerBestiary` — `@@id([playerId, mobTemplateId])` ✅
- `PlayerBestiaryPrefix` — `@@id([playerId, mobTemplateId, prefix])` ✅
- `PvpRating` — `@@unique(playerId)` ✅
- `PlayerZoneDiscovery` — `@@index([playerId])` ✅
- `PlayerZoneExploration` — `@@index([playerId])` ✅
- `PlayerRecipe` — `@@id([playerId, recipeId])` ✅
- `PlayerSkill` — `@@unique([playerId, skillType])` ✅
- `GuildMember` — `@@unique(playerId)` ✅
- `MobFamilyMember` — `@@index([mobTemplateId])` ✅

### Payload Bloat

**1. `resolveStats` calls `resolveAllStats` even for 1 key (lines 176–185)**
Requesting a single stat key (e.g., `totalKills` for an achievement check) triggers the entire 12-subquery raw SQL, guild stats query, and playerStats fetch. For the combat achievement path, only 1–2 stat keys are needed.

```ts
export async function resolveStats(playerId: string, statKeys: string[]): Promise<Record<string, number>> {
  const all = await resolveAllStats(playerId);  // always runs the FULL query
  // ... pick subset ...
}
```

**2. `playerStats.findUnique` — no `select` (line 139)**
Fetches full `PlayerStats` row. Uses most fields (10 counters), so largely justified.

### Cache Issues

**No Redis usage.**

| Function | Call Frequency | Data Volatility | Cache Candidate? |
|----------|---------------|----------------|-----------------|
| `resolveAllStats` | Every achievements page | Changes on combat/craft/etc. | Moderate — short TTL (30s) |
| `resolveStats` (subset) | Every combat achievement check | Same | **Strong** — hot path, short TTL |
| `resolveGuildStats` | Part of `resolveAllStats` | Changes on guild events | Same as above |

The mega raw SQL query is expensive (12 correlated subqueries). Short-TTL caching would reduce DB load on the achievements page, which can be refreshed repeatedly by players.

### Migration Risks

None. Raw SQL queries are well-structured with proper parameterization and COALESCE fallbacks.

## Suggested Fixes

### Priority 1 — Add `@@index([playerId])` on `BossParticipant`

```prisma
model BossParticipant {
  // ... existing fields ...
  @@index([playerId])  // ← add this
}
```

Enables efficient `player_id` lookups for boss kill/damage stats. Without this, the `resolveAllStats` query scans the entire `boss_participants` table for each player.

### Priority 2 — Subset-optimized `resolveStats`

For hot-path callers (combat achievement checks needing 1–2 keys), build targeted queries instead of the full mega query:

```ts
export async function resolveStats(playerId: string, statKeys: string[]): Promise<Record<string, number>> {
  if (statKeys.length <= 3) {
    return resolveStatsByKey(playerId, statKeys); // targeted queries
  }
  const all = await resolveAllStats(playerId);    // full batch for many keys
  return pick(all, statKeys);
}
```

### Priority 3 — Short-TTL cache for `resolveAllStats`

```ts
const cacheKey = `stats:all:${playerId}`;
const cached = await redis.get(cacheKey);
if (cached) return JSON.parse(cached);

const result = await computeAllStats(playerId);
await redis.set(cacheKey, JSON.stringify(result), 'EX', 30); // 30s TTL
return result;
```

Prevents rapid-refresh abuse on the achievements page.
