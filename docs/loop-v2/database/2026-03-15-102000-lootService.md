# Database Audit: lootService

**Date:** 2026-03-15
**Service:** `apps/api/src/services/lootService.ts` (160 lines, 3 exported functions)

## Prisma Models Touched

Direct: `DropTable`, `ItemTemplate`, `Item`
Via sub-services: `PlayerEquipment` (via `getInventoryState`), Redis (via `storePendingLoot`)

---

## Findings

### N+1 Queries

**1. Per-drop stack existence check (line 56)**
For each stackable drop, a `findFirst` checks if the player already has a stack. Could batch-fetch all relevant template stacks upfront.

```ts
for (const entry of entries) {
  // ...
  if (entry.itemTemplate.stackable) {
    const existing = await prisma.item.findFirst({
      where: { ownerId: playerId, templateId: entry.itemTemplateId, inStash: false },
    });
    // ...
  }
}
```

**2. `addStackableItem` re-queries what was just checked (line 71)**
`addStackableItem` internally calls `itemTemplate.findUnique` (to verify stackable) + `item.findFirst` (to find existing stack) — both were already determined by the loop above. The stack check at line 56 and the one inside `addStackableItem` are redundant.

```ts
// Line 56: checks for existing stack
const existing = await prisma.item.findFirst({ where: { ownerId, templateId, inStash: false } });
// Line 71: addStackableItem internally does the SAME findFirst + a findUnique for template
await addStackableItem(playerId, entry.itemTemplateId, quantity);
```

**3. Per non-stackable item creation (lines 102–112)**
Each non-stackable drop creates items one at a time. A mob dropping 3 pieces of armor triggers 3 sequential `item.create` calls.

```ts
for (let i = 0; i < quantity; i++) {
  // ... roll rarity + bonus stats ...
  await prisma.item.create({ data: { ... } });
}
```

**Total per combat:** For a mob with 5 drop table entries where 3 drops succeed (2 stackable, 1 non-stackable):
- 1 dropTable.findMany
- 2 getInventoryState queries
- 2× findFirst (stack check) + 2× addStackableItem (2-3 queries each) = ~8 queries for stackables
- 1× item.create for non-stackable
- **Total: ~12 queries** (could be 4-5 with batching)

### Missing Indexes

**1. `DropTable.mobTemplateId` — no explicit index (already identified)**
The `dropTable.findMany({ where: { mobTemplateId } })` query runs on every combat. `DropTable` has no `@@index([mobTemplateId])`.

```ts
prisma.dropTable.findMany({
  where: { mobTemplateId },
  include: { itemTemplate: true },
});
```

**2. `Item(ownerId, templateId, inStash)` — no index (already identified)**
The stack existence check `item.findFirst({ ownerId, templateId, inStash: false })` uses this filter pattern.

### Payload Bloat

**1. `include: { itemTemplate: true }` on drop table fetch (line 32)**
Fetches full `ItemTemplate` (14 columns) for each drop table entry. Uses 6 fields: `stackable`, `name`, `itemType`, `maxDurability`, `baseStats`, `slot`.

```ts
prisma.dropTable.findMany({
  where: { mobTemplateId },
  include: { itemTemplate: true },  // 14 columns, uses 6
});
```

**2. Stack check `findFirst` without select (line 56)**
Fetches full `Item` row but only checks existence (`!existing`).

```ts
const existing = await prisma.item.findFirst({
  where: { ownerId: playerId, templateId: entry.itemTemplateId, inStash: false },
  // no select — full Item row for null check
});
```

### Cache Issues

**1. `dropTable.findMany({ where: { mobTemplateId } })` — STATIC game data, never cached**
Drop tables are seed data that never changes at runtime. This query runs on every single combat but the result is identical every time. This is the strongest cache candidate in the inventory domain.

```
Call frequency: Every PvE combat
Data volatility: Never (admin-only changes)
Cache TTL: Long (hours/days) or event-invalidated on admin data reload
Savings: 1 query + join per combat
```

**No Redis usage for reads** (only `storePendingLoot` writes to Redis for overflow).

### Migration Risks

None specific to this service.

## Suggested Fixes

### Priority 1 — Cache drop tables

Drop tables are static game data. Cache with long TTL:

```ts
const cacheKey = `droptable:${mobTemplateId}`;
const cached = await redis.get(cacheKey);
if (cached) return JSON.parse(cached);

const entries = await prisma.dropTable.findMany({
  where: { mobTemplateId },
  select: { /* only needed fields */ },
});
await redis.set(cacheKey, JSON.stringify(entries), 'EX', 86400); // 24h
```

Invalidate on: admin data reload / seed.

### Priority 2 — Batch stack existence checks

Pre-fetch all existing stacks for the player's drop templates in one query:

```ts
const stackableTemplateIds = entries
  .filter(e => e.itemTemplate.stackable)
  .map(e => e.itemTemplateId);

const existingStacks = await prisma.item.findMany({
  where: { ownerId: playerId, templateId: { in: stackableTemplateIds }, inStash: false },
  select: { id: true, templateId: true, quantity: true },
});
const stackMap = new Map(existingStacks.map(s => [s.templateId, s]));
```

Then use `stackMap.get(templateId)` in the loop instead of per-drop `findFirst`. Saves N-1 queries for stackable drops.

### Priority 3 — Inline stackable item granting

Instead of calling `addStackableItem` (which re-queries template + stack), use the data already available:

```ts
if (existingStack) {
  await prisma.item.update({
    where: { id: existingStack.id },
    data: { quantity: existingStack.quantity + quantity },
  });
} else {
  await prisma.item.create({ data: { ownerId, templateId, quantity, rarity: 'common', ... } });
}
```

Eliminates the redundant `itemTemplate.findUnique` + `item.findFirst` inside `addStackableItem`.

### Priority 4 — Batch non-stackable creates

Use `createMany` for drops of the same template (when no bonus stats vary):

```ts
// For items with individual bonus stats, still need individual creates
// But can use createManyAndReturn or batch where possible
await prisma.item.createMany({
  data: itemsToCreate,
});
```

Note: each non-stackable item has individually rolled `rarity` and `bonusStats`, so `createMany` works but bonus stats must be pre-computed.

### Priority 5 — Add missing indexes

(Already recommended in prior audits):
- `@@index([mobTemplateId])` on `DropTable`
- `@@index([ownerId, templateId, inStash])` on `Item`
