# Database Audit: chestService

**Date:** 2026-03-15
**Service:** `apps/api/src/services/chestService.ts` (137 lines, 1 exported function)

## Prisma Models Touched

Direct: `ChestDropTable`, `ItemTemplate`, `CraftingRecipe`, `PlayerRecipe`
Via sub-service: `Item`, `ItemTemplate` (via `rollAndGrantDropsTx`)

---

## Findings

### N+1 Queries

No direct N+1 in this service. Transitive N+1 comes from `rollAndGrantDropsTx` (already audited in dropRollingService).

### Missing Indexes

**No issues.** All queries are well-indexed:
- `ChestDropTable` uses `@@index([mobFamilyId, chestRarity])` — exact match for lines 51–65
- `CraftingRecipe` uses `@@index([isAdvanced])` and `@@index([mobFamilyId])` — cover the recipe query
- `PlayerRecipe` uses `@@id([playerId, recipeId])` — PK prefix covers the known-recipe check

### Payload Bloat

**No issues.** This is one of the cleanest services for `select` usage:

```ts
// ChestDropTable — select on join
include: { itemTemplate: { select: { itemType: true, stackable: true, maxDurability: true } } }

// CraftingRecipe — minimal select
select: { id: true, resultTemplateId: true, soulbound: true, resultTemplate: { select: { name: true } } }

// PlayerRecipe — minimal select
select: { recipeId: true }
```

### Cache Issues

**1. `chestDropTable.findMany({ mobFamilyId, chestRarity })` — static game data (line 51)**
Chest drop tables are seed data, same as regular drop tables. Could be cached with long TTL. Lower priority than `DropTable` since chest opening is less frequent.

**2. `craftingRecipe.findMany({ isAdvanced, mobFamilyId })` — static game data (line 76)**
Advanced recipes per mob family don't change at runtime.

Both are cacheable but the frequency of chest opening is low enough that the impact is moderate.

### Migration Risks

None.

## Query Patterns

### `grantEncounterSiteChestRewardsTx` — 2–5 direct + N transitive queries

| Step | Query | Index | Select? |
|------|-------|-------|---------|
| 1 | `chestDropTable.findMany({ mobFamilyId, chestRarity })` | `@@index([mobFamilyId, chestRarity])` | Yes (join select) |
| 2 | `rollAndGrantDropsTx(...)` | Various | — (transitive N+1) |
| 3 | `craftingRecipe.findMany({ isAdvanced, mobFamilyId })` | `@@index([isAdvanced])` + `@@index([mobFamilyId])` | Yes |
| 4 | `playerRecipe.findMany({ playerId, recipeId: { in } })` | `@@id([playerId, recipeId])` | Yes |
| 5 | `playerRecipe.create(...)` | — | — |

Steps 3–5 only execute when recipe chance roll succeeds.

**Typical total (with recipe roll miss):** 1 + ~12 (rollAndGrant) = **~13 queries**
**With recipe roll hit:** 1 + ~12 + 3 = **~16 queries**

## Suggested Fixes

### Priority 1 — Cache static chest drop tables (optional)

```ts
const cacheKey = `chest-drops:${mobFamilyId}:${chestRarity}`;
```

Lower impact than `DropTable` caching since chest opening is infrequent. Could share a caching layer if `DropTable` caching is implemented.

### No other fixes needed

This service is well-designed:
- Proper `select` on all queries and joins
- All queries hit appropriate indexes
- Good use of conditional queries (recipe roll only queries DB on success)
- Proper transaction usage
- Recipe dedup with `playerRecipe` known-set check prevents duplicates
