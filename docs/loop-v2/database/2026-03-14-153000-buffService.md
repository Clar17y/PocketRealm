## Findings

### N+1 Queries

**1. `consumeBuffChargesPerMob` — up to 3 sequential `consumeBuffIfActive` calls (lines 121–123)**
Each `consumeBuffIfActive` does: `findUnique` + `update` + possibly `delete` (1–3 queries). With all 3 buff types active, this is 6–9 sequential queries inside a transaction.

```ts
if (uses.damage > 0) { await consumeBuffIfActive(tx, playerId, 'combat_damage'); uses.damage--; }
if (uses.defence > 0) { await consumeBuffIfActive(tx, playerId, 'combat_defence'); uses.defence--; }
if (uses.durability > 0) { await consumeBuffIfActive(tx, playerId, 'durability_shield'); uses.durability--; }
```

**2. `consumeCombatBuffs` — same pattern (lines 146–148)**
Up to 3 sequential `consumeBuffIfActive` calls.

```ts
if (buffs.damageBoost > 0) await consumeBuffIfActive(tx, playerId, 'combat_damage');
if (buffs.defenceBoost > 0) await consumeBuffIfActive(tx, playerId, 'combat_defence');
if (buffs.durabilityShield > 0) await consumeBuffIfActive(tx, playerId, 'durability_shield');
```

**Both could be replaced with:**
- Single `updateMany` to decrement all active combat buffs
- Single `deleteMany` to remove those with `remainingUses <= 0`

### Missing Indexes

No issues. All queries use `@@unique([playerId, buffType])` — exact match or prefix scan.

### Payload Bloat

**1. `getActiveBuffs` — no `select` on main model (line 11)**
Fetches full `PlayerBuff` rows (including `shopItemId`, `createdAt`) when the response only uses `id`, `buffType`, `remainingUses`, `bonusValue`, `createdAt`. Minor — the row is small (7 fields), and most fields are used.

```ts
prisma.playerBuff.findMany({
  where: { playerId },
  include: { shopItem: { select: { name: true } } },  // good: select on join
  // but no select on main model
});
```

### Cache Issues

**No Redis usage.**

| Function | Call Frequency | Data Volatility | Cache Candidate? |
|----------|---------------|----------------|-----------------|
| `getCombatBuffs` / `getCombatBuffsWithUses` | Every combat | Changes only on purchase or consume | Weak — consumed during combat makes caching complex |
| `getBuffValue` / `hasActiveBuff` | On-demand checks | Same | Weak |
| `getActiveBuffs` | UI display | Same | Weak — low frequency |

Buff caching is low-value because buffs are consumed during the same transaction that would need to invalidate the cache. The read-before-write pattern (`consumeBuffIfActive`) is inherent to the consumption logic.

### Migration Risks

**1. `ShopItem` cascade delete removes active player buffs (line 1268 of schema)**
`shopItem ShopItem @relation(..., onDelete: Cascade)` means deleting a `ShopItem` silently removes all `PlayerBuff` records referencing it. If shop items are ever restructured (renamed, merged, deprecated), active player buffs disappear without warning.

```prisma
shopItem ShopItem @relation(fields: [shopItemId], references: [id], onDelete: Cascade)
```

## Suggested Fixes

### Priority 1 — Batch buff consumption

Replace sequential `consumeBuffIfActive` calls with bulk operations:

```ts
export async function consumeCombatBuffsBatched(
  tx: any, playerId: string, buffTypes: string[],
): Promise<void> {
  // Decrement all in one query
  await tx.playerBuff.updateMany({
    where: { playerId, buffType: { in: buffTypes } },
    data: { remainingUses: { decrement: 1 } },
  });
  // Clean up exhausted buffs
  await tx.playerBuff.deleteMany({
    where: { playerId, buffType: { in: buffTypes }, remainingUses: { lte: 0 } },
  });
}
```

Reduces 6–9 queries to 2 for combat buff consumption.

### Priority 2 — Fix cascade risk

Change `ShopItem` relation to `onDelete: Restrict` or `onDelete: SetNull` (requires making `shopItemId` optional). This prevents accidental buff deletion when shop items are modified.

### Priority 3 — Type safety

Replace `(prisma as any)` casts with proper Prisma types. This suggests `PlayerBuff` may have been added to the schema after the initial Prisma client generation, or there's a type mismatch. Running `npm run db:generate` should resolve it.
