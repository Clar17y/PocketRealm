## Findings

### N+1 Queries

**1. `scoutOpponent` — duplicate target equipment fetch (lines 165–177)**
Target equipment is fetched twice: once directly via `playerEquipment.findMany` (line 166) and again inside `calculatePowerRating(targetId)` which calls `getEquipmentStats(targetId)`. Both queries fetch full equipment with `include: { item: { include: { template: true } } }`.

```ts
const [targetEquipment, [targetPower, myPower], ...] = await Promise.all([
  prisma.playerEquipment.findMany({                    // fetch #1
    where: { playerId: targetId, itemId: { not: null } },
    include: { item: { include: { template: true } } },
  }),
  Promise.all([calculatePowerRating(targetId), ...]),  // fetch #2 (via getEquipmentStats)
  ...
]);
```

**2. `challenge` — sequential validation queries (lines 307–378)**
Seven sequential queries before combat begins. Several could be parallelized:

```
1. getHpState(attackerId)               — sequential (gate)
2. player.findUnique(attackerId)        — sequential (gate: zone check)
3. pvpCooldown.findUnique               — could parallel with #4
4. player.findUnique(targetId)          — could parallel with #3
5. getOrCreateRating(attackerId)        — could parallel with #6
6. getOrCreateRating(targetId)          — could parallel with #5
7. pvpMatch.findFirst (revenge check)   — depends on #5/#6
```

**3. `challenge` — `getAttackStyle` called separately from `buildPvpCombatant` (lines 383–388)**
Both `buildPvpCombatant` and `getAttackStyle` query the player's equipment. Each `buildPvpCombatant` call already fetches equipment internally, but `getAttackStyle` is a separate call that also reads the main-hand weapon. For two players, this means equipment is queried 4 times instead of 2.

```ts
const [attackerCombatant, defenderCombatant, attackStyle, defenderStyle] = await Promise.all([
  buildPvpCombatant(attackerId, ...),   // fetches equipment
  buildPvpCombatant(targetId, ...),     // fetches equipment
  getAttackStyle(attackerId),           // re-fetches main hand
  getAttackStyle(targetId),             // re-fetches main hand
]);
```

### Missing Indexes

**1. `PvpRating.rating` — no index for range query in `getLadder` (line 75)**
The ladder query filters by `rating: { gte, lte }` with `orderBy: { rating: 'desc' }`. No `@@index([rating])` exists — requires full table scan + sort.

```ts
prisma.pvpRating.findMany({
  where: { playerId: { not: playerId }, rating: { gte: widestLower, lte: widestUpper }, ... },
  orderBy: { rating: 'desc' },
});
```

**2. `PvpMatch` — missing `@@index([defenderId, defenderRead])` for notifications (lines 655, 665)**
`getNotificationCount` and `getNotifications` filter by `{ defenderId, defenderRead: false }`. The existing `@@index([defenderId, createdAt])` covers `defenderId` prefix but requires scanning all defender matches to filter by `defenderRead`. Polled on every page load.

```ts
prisma.pvpMatch.count({ where: { defenderId: playerId, defenderRead: false } });
prisma.pvpMatch.findMany({ where: { defenderId: playerId, defenderRead: false }, ... });
```

**3. `PvpCooldown` — `(attackerId, expiresAt)` not covered for `getLadder` (line 64)**
Cooldown query filters `{ attackerId, expiresAt: { gt: new Date() } }`. The `@@unique([attackerId, defenderId])` covers `attackerId` prefix but `expiresAt` requires scanning all cooldowns for that attacker.

```ts
prisma.pvpCooldown.findMany({
  where: { attackerId: playerId, expiresAt: { gt: new Date() } },
  select: { defenderId: true },
});
```

### Payload Bloat

**1. `getHistory` — fetches `combatLog` JSON blob, doesn't return it (lines 575–605)**
`findMany` fetches full `PvpMatch` rows including the large `combatLog` JSON column, but the response mapping (lines 589–604) explicitly excludes it. Should use `select` to skip `combatLog`.

```ts
prisma.pvpMatch.findMany({
  where,
  include: { attacker: { select: { username: true } }, defender: { select: { username: true } } },
  // ← fetches combatLog, attackerRead, defenderRead, etc. — all unused
});
```

**2. `getNotifications` — fetches full match including `combatLog` (lines 665–672)**
Notifications only need attacker name, ratings, outcome, and timestamp — not the full combat log JSON. No `select` used.

```ts
prisma.pvpMatch.findMany({
  where: { defenderId: playerId, defenderRead: false },
  include: { attacker: { select: { username: true } } },
  // ← fetches entire combatLog JSON for every unread notification
});
```

**3. `scoutOpponent` — equipment with full `include: { template: true }` (line 168)**
Fetches complete `ItemTemplate` rows for all equipped items. Only uses `requiredSkill` and `weightClass` (lines 181, 188).

### Cache Issues

**No Redis usage anywhere in the service.**

| Function | Call Frequency | Data Volatility | Cache Candidate? |
|----------|---------------|----------------|-----------------|
| `getOrCreateRating` | Every ladder view + every challenge | Changes only on match completion | **Strong** — 60s TTL, invalidate on challenge |
| `getNotificationCount` | Every page load (poll) | Changes on incoming challenge | **Strong** — short TTL or push-invalidated |
| `getLadder` (candidates) | Every ladder view | Changes on any match completion | Moderate — short TTL |

### Migration Risks

**1. `PvpCooldown` — no FK relation to Player**
The `PvpCooldown` model has `attackerId` and `defenderId` string columns but no `@relation` to `Player`. If a player is deleted, their cooldowns become orphan rows.

```prisma
model PvpCooldown {
  attackerId String   @map("attacker_id")
  defenderId String   @map("defender_id")
  // No player relation — no cascade delete
}
```

**2. `PvpMatch.combatLog` — unbounded JSON blob**
The `combatLog` column stores the entire combat log as JSON. Long fights (high round counts) produce large blobs. No compression or size limit — and this column is fetched in `getNotifications` and `getHistory` even when not needed.

## Suggested Fixes

### Priority 1 — Add missing indexes

1. **`@@index([rating])` on `PvpRating`** — enables efficient range scan for ladder
2. **`@@index([defenderId, defenderRead])` on `PvpMatch`** — notification queries polled on every page load
3. **`@@index([attackerId, expiresAt])` on `PvpCooldown`** — covers ladder cooldown check

### Priority 2 — Eliminate payload bloat

4. **`getHistory`** — use `select` to exclude `combatLog`:
```ts
prisma.pvpMatch.findMany({
  where,
  select: {
    id: true, attackerId: true, defenderId: true,
    attackerRating: true, defenderRating: true,
    attackerRatingChange: true, defenderRatingChange: true,
    attackerStyle: true, defenderStyle: true,
    winnerId: true, isRevenge: true, turnsSpent: true, createdAt: true,
    attacker: { select: { username: true } },
    defender: { select: { username: true } },
  },
});
```

5. **`getNotifications`** — same treatment, exclude `combatLog`

### Priority 3 — Deduplicate equipment fetches

6. **`scoutOpponent`** — pass pre-fetched `targetEquipment` into `calculatePowerRating` instead of re-fetching via `getEquipmentStats`
7. **`challenge`** — have `buildPvpCombatant` return attack style so `getAttackStyle` doesn't re-query equipment

### Priority 4 — Parallelize validation in `challenge`

8. Run cooldown check + target fetch + rating fetches in parallel after the gate checks (HP + zone):
```ts
const [cooldown, target, attackerRating, defenderRating] = await Promise.all([
  prisma.pvpCooldown.findUnique({ where: { attackerId_defenderId: { attackerId, defenderId: targetId } } }),
  prisma.player.findUnique({ where: { id: targetId }, select: { ... } }),
  getOrCreateRating(attackerId),
  getOrCreateRating(targetId),
]);
```

### Priority 5 — Cache notification count

9. Cache `getNotificationCount` in Redis with 30s TTL, invalidated when a new PvP match is created.

### Priority 6 — Fix orphan risk

10. Add `@relation` to `Player` on `PvpCooldown.attackerId` and `defenderId` with `onDelete: Cascade`.
