# Database Audit: xpService

**Date:** 2026-03-15
**Service:** `apps/api/src/services/xpService.ts` (153 lines, 1 exported function)

## Prisma Models Touched

Direct: `Player`, `PlayerSkill`
Via sub-services: `PlayerBuff` (via `consumeBuffIfActive`), `GuildMember`, `GuildUpgrade`, `GuildProject`, `Guild` (via `getPlayerGuildModifiers`)

---

## Findings

### N+1 Queries

No N+1 in this service directly. The N+1 comes from callers — `splitAndGrantXp` in combatOrchestrationService calls `grantSkillXp` 1–3 times sequentially, each opening its own transaction with a row lock (6–24 queries for XP granting per combat).

### Missing Indexes

No issues. All queries use well-indexed paths:
- `PlayerSkill` via `@@unique([playerId, skillType])` — exact match
- `Player` via PK
- `PlayerBuff` via `@@unique([playerId, buffType])` (inside `consumeBuffIfActive`)

### Payload Bloat

**1. `playerSkill.findUnique` — no `select` (lines 54–58)**
Fetches full `PlayerSkill` row (7 fields: id, playerId, skillType, level, xp, dailyXpGained, lastXpResetAt). Uses 4 fields: `xp`, `level`, `dailyXpGained`, `lastXpResetAt`. Minor — row is small.

```ts
tx.playerSkill.findUnique({
  where: { playerId_skillType: { playerId, skillType } },
  // no select — fetches all 7 fields, uses 4
});
```

The `player.findUnique` at line 59 properly uses `select: { characterXp, characterLevel, attributePoints }` — good pattern.

### Cache Issues

**1. `getPlayerGuildModifiers(playerId)` — 4–5 queries outside tx (line 34)**
Called when `guildXpBoost` is not provided by the caller. In the combat path, `guildXpBoost` IS passed from `splitAndGrantXp`, so this is skipped. Only fires for non-combat XP grants (training, etc.).

Already flagged in prior audits — `getPlayerGuildModifiers` is the strongest cache candidate for guild data.

### Migration Risks

None. The transaction patterns are correct:
- `FOR UPDATE` row lock prevents concurrent level-up races
- Atomic `increment` on `characterXp` and `attributePoints` prevents overwrites
- Buff consumption inside tx prevents double-apply

## Query Patterns

### `grantSkillXp` — 6–8 queries (inside tx)

| Step | Query | Index | Notes |
|------|-------|-------|-------|
| 0 | `getPlayerGuildModifiers` (outside tx) | Various | **Skipped if guildXpBoost provided** |
| 1 | `$queryRaw SELECT ... FOR UPDATE` | PK | Row lock |
| 2 | `consumeBuffIfActive` (findUnique + update + maybe delete) | `@@unique([playerId, buffType])` | 1–3 queries |
| 3a | `playerSkill.findUnique` | `@@unique([playerId, skillType])` | Parallel with 3b |
| 3b | `player.findUnique` with select | PK | Parallel with 3a |
| 4 | `playerSkill.update` | `@@unique([playerId, skillType])` | |
| 5 | `player.update` with atomic increment | PK | |

**Combat path (guildXpBoost provided):** 6–8 queries per call
**Non-combat path (guildXpBoost not provided):** 10–13 queries per call

**Per combat (1–3 skills):** 6–24 queries total for XP granting

## Suggested Fixes

### Priority 1 — Add `select` to `playerSkill.findUnique`

```ts
tx.playerSkill.findUnique({
  where: { playerId_skillType: { playerId, skillType } },
  select: { xp: true, level: true, dailyXpGained: true, lastXpResetAt: true },
});
```

Minor impact — saves ~3 unused fields per call.

### Priority 2 — Batch multi-skill XP grants (caller-level fix)

The real optimization is in `splitAndGrantXp` (combatOrchestrationService): when XP is split across 2–3 skills, each gets its own `grantSkillXp` call with its own transaction + row lock + buff consumption. A combined `grantMultiSkillXp` function could:
1. Lock the player row once
2. Consume the XP buff once
3. Fetch all relevant PlayerSkill records in one `findMany`
4. Update all in sequence within one transaction

This would reduce 3× (6–8) = 18–24 queries to ~10 queries for a 3-skill combat.

### No other fixes needed

This service has solid transaction safety:
- `FOR UPDATE` prevents double level-up
- Atomic increments prevent concurrent overwrites
- Buff consumption inside tx prevents double-apply
- Parallel reads with `Promise.all`
