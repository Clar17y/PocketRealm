# Database Audit: sparService

**Date:** 2026-03-14
**Service:** `apps/api/src/services/sparService.ts` (150 lines, 4 exported functions)

## Prisma Models Touched

Direct: `Friendship`, `Player`
Via sub-services: `PlayerEquipment`, `Item`, `ItemTemplate`, `PlayerSkill`, `CombatTemplate`, `CombatTemplateSlot`, `SkillPointAllocation`, `TurnBank`, `PlayerBlock`, `FriendMail`

---

## Findings

### N+1 Queries

No N+1 issues in this service directly. The transitive cost comes from `buildPvpCombatant` (×2), already audited — ~25 queries for two combatants.

### Missing Indexes

No issues. All direct queries use well-indexed paths:
- `Friendship` lookup via `@id` (PK) — efficient even with the `status` + `OR` filter
- `Friendship` also has `@@index([senderId, status])` and `@@index([receiverId, status])`
- `Player` via PK

### Payload Bloat

No issues. The only direct Prisma call uses `select: { username: true }` (line 103) — minimal.

```ts
prisma.player.findUniqueOrThrow({
  where: { id: defenderId },
  select: { username: true },
});
```

### Cache Issues

No Redis usage, but no strong cache candidates either. Sparring is infrequent (friend-only, costs turns), so caching the friendship or block check wouldn't provide meaningful benefit.

### Migration Risks

None specific to this service. Friendship cascade deletes are correct (player deletion removes friendships).

## Query Patterns

| Query | Select/Include | Index |

| Query | Index |

### `runSpar` — ~27 queries total

| Phase | Queries | Details |
|-------|---------|---------|
| Defender username | 1 | `player.findUniqueOrThrow` with select |
| Build 2 combatants | ~25 | 2× `buildPvpCombatant` (see pvpCombatantBuilder audit) |
| Spar result mail | 1 | Fire-and-forget `sendSystemMail` |
| **Total** | **~27** | |

**Note:** Unlike PvP `challenge`, sparring has no post-combat state changes (no HP loss, no rating change, no durability degradation, no loot). The query cost is almost entirely in combatant building.

## Suggested Fixes

No direct fixes needed for this service. All optimization opportunities are in the transitive dependencies:

1. **`buildPvpCombatant` optimizations** (see pvpCombatantBuilder audit) would reduce combatant building from ~25 to ~14 queries — largest impact here.
2. The `validateSpar` → `runSpar` flow is already well-structured with proper gating (validate first, build combatants only after passing validation).
