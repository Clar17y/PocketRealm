### Error Handling
- [medium] **TOCTOU race on duplicate-block check (lines 26-35)** — The `findUnique` check for an existing block (line 26) runs *outside* the transaction (line 34). Two concurrent `blockPlayer` calls for the same pair could both pass the check, then one would hit a unique constraint violation (`P2002`) inside the transaction with an unhandled Prisma error instead of the clean `AppError('ALREADY_BLOCKED')`. — **Suggested fix:** Move the existence check inside the transaction, or use `createMany({ skipDuplicates: true })` / catch `P2002` and rethrow as `AppError`.

- [low] **Two `deleteMany` calls could be combined (lines 40-59)** — The transaction runs two separate `deleteMany` calls on the `friendship` table — one for `status: 'accepted'` and one for `status: 'pending'`. These could be a single `deleteMany` with `status: { in: ['accepted', 'pending'] }` (or no status filter if those are the only two states). Not a correctness issue, but an unnecessary extra DB round-trip. — **Suggested fix:** Combine into one `deleteMany` with an `OR` on both player directions and `status: { in: ['accepted', 'pending'] }`.
