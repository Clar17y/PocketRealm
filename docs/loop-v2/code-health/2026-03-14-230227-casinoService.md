## Findings

### Type Safety
- [medium] **Unvalidated `JSON.parse` from Redis throughout (lines 73, 84, 193, 229, 257)** — Five `JSON.parse` calls on Redis strings, each producing `any` or directly assigned to a typed variable without runtime validation. Line 73: `const parsed: ActiveRound = JSON.parse(existing)` — a corrupted/unexpected Redis value would create a malformed `ActiveRound` object. Line 84 and 229: `JSON.parse(resolved)` destructured/accessed with no type checking. If Redis data is corrupted (e.g., partial write, wrong key), the code silently produces garbage values. — **Suggested fix:** Add a thin parse-and-validate utility: `function parseActiveRound(raw: string): ActiveRound { const obj = JSON.parse(raw); if (!obj.roundId || typeof obj.startedAt !== 'number') throw new Error('Invalid round'); return obj; }`.

- [medium] **`betType as RouletteBetType` cast on DB values (lines 124, 125, 162, 296)** — `bet.betType` is a `string` from Prisma, cast to `RouletteBetType` without validation. If the DB contains an unexpected value (e.g., from a schema migration or manual edit), it passes through silently. — **Suggested fix:** Validate with a set check: `if (!VALID_BET_TYPES.has(bet.betType)) continue;` before casting.

- [low] **Non-null assertions on filtered query results (lines 310, 372, 373, 386)** — `validation.error!`, `r.result!`, and `r.resolvedAt!` use `!` where the value is logically non-null (filtered by `where` clause or `!valid` check) but TypeScript can't verify it. — **Suggested fix:** Use nullish coalescing fallbacks: `validation.error ?? 'Invalid bet'`, `r.result ?? 0`, `r.resolvedAt ?? new Date()`.

### Error Handling
- [high] **Polling fallback returns valid-looking `0` on lock contention (lines 105-113)** — When another process holds the resolution lock, this code polls 10 times (3 seconds total), then returns `0` — which is a valid roulette number (green zero). This means a timeout during lock contention silently produces a "result" of 0 instead of an error. Players could see an incorrect result. — **Suggested fix:** Throw an error instead of returning `0`: `throw new Error('Round resolution timed out')`. Or return the actual resolved result by re-reading the round after the loop.

- [low] **Post-transaction achievement tracking not error-isolated (lines 176-189)** — If `checkAchievements` or `emitAchievementNotifications` throws for any winner, the remaining winners' achievements are skipped. Gold distribution is already committed, so the function continues with no rollback needed, but the thrown error propagates to the caller. — **Suggested fix:** Wrap in try/catch per winner: `try { ... } catch (err) { logger.warn('Achievement check failed', { playerId: wId, err }); }`.
