# Frontend Audit: Templates

**Component Audited:** `apps/web/src/components/screens/Templates.tsx` (801 lines)
**Date:** 2026-03-14

---

## Accessibility

### 1. Back buttons lack aria-label
**Severity:** medium
**Lines:** 392-394, 441-444

Both the action picker and editor views use `<ChevronLeft>` icon buttons for navigation with no `aria-label`. Screen readers announce these as unlabeled buttons.

**Suggested Fix:** Add `aria-label="Back"` to both buttons.

### 2. Slot reorder/remove buttons lack aria-labels
**Severity:** medium
**Lines:** 518-537

The ArrowUp, ArrowDown, and X buttons for each slot have no `aria-label`. Touch targets are correctly sized (`min-w-[36px] min-h-[36px]`) but screen readers can't identify their purpose.

**Suggested Fix:**
```tsx
<button aria-label={`Move slot ${i + 1} up`} ...><ArrowUp /></button>
<button aria-label={`Move slot ${i + 1} down`} ...><ArrowDown /></button>
<button aria-label={`Remove slot ${i + 1}`} ...><X /></button>
```

### 3. Expandable slot row not keyboard accessible
**Severity:** medium
**Lines:** 492-494

The slot collapse/expand toggle uses a `<div onClick>` with no `role`, `tabIndex`, or keyboard handler. Keyboard users cannot expand slots to edit conditions.

**Suggested Fix:** Add `role="button"`, `tabIndex={0}`, and an `onKeyDown` handler for Enter/Space:
```tsx
<div
  role="button"
  tabIndex={0}
  onClick={() => setExpandedSlot(isExpanded ? null : i)}
  onKeyDown={e => { if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); setExpandedSlot(isExpanded ? null : i); }}}
  ...
>
```

### 4. Form labels not programmatically associated with inputs
**Severity:** low
**Lines:** 549-558, 563, 580-583

The condition `<select>`, threshold `<input>`, and effect name `<select>` have `<label>` elements but are not linked via `htmlFor`/`id`. Clicking the label doesn't focus the input.

**Suggested Fix:** Add matching `id` and `htmlFor` attributes to each label/input pair.

## Component Duplication

### 1. Error banner could use existing `ErrorBanner` component
**Severity:** low
**Lines:** 450-453

The inline error banner uses the same pattern as other screens (`bg-[var(--rpg-red)]/10 border border-[var(--rpg-red)]`). The app has `components/common/ErrorBanner.tsx` which could be reused.

**Suggested Fix:** Replace inline error div with `<ErrorBanner message={error} />` if the component's API matches, or extend it.

## State Issues

### 1. `handleActivate` and `handleDelete` have no error handling
**Severity:** medium
**Lines:** 205-213

Both API calls (`activateTemplate`, `deleteTemplate`) and the subsequent `onLoadTemplates()` are not wrapped in try/catch. If they fail, the promise rejection is unhandled and the user gets no feedback.

**Suggested Fix:**
```tsx
const handleActivate = useCallback(async (id: string) => {
  try {
    await activateTemplate(id);
    await onLoadTemplates();
  } catch {
    setError('Failed to activate template');
  }
}, [onLoadTemplates]);
```
Same pattern for `handleDelete`.

### 2. Grouped actions computed every render
**Severity:** low
**Lines:** 365-371

`Object.values(BASE_ACTION_DEFINITIONS)` and the grouping loop run on every render. Since `BASE_ACTION_DEFINITIONS` is a module-level constant, the grouped result could be precomputed at module level or wrapped in `useMemo`.

**Suggested Fix:** Move the grouping outside the component:
```tsx
const GROUPED_ACTIONS: Record<string, ActionDefinition[]> = {};
for (const group of GROUP_ORDER) GROUPED_ACTIONS[group] = [];
for (const def of Object.values(BASE_ACTION_DEFINITIONS)) {
  const group = ACTION_GROUPS[def.id] ?? 'Basic';
  GROUPED_ACTIONS[group]?.push(def);
}
```

## UX Issues

### 1. Delete button has no confirmation dialog
**Severity:** high
**Lines:** 790-792

Clicking "Delete" immediately removes the template with no confirmation. Templates with complex conditional logic take significant time to build. There's no undo mechanism.

**Suggested Fix:** Use `ConfirmModal` (already available in `components/common/`):
```tsx
const [confirmDelete, setConfirmDelete] = useState<string | null>(null);
// ...
<PixelButton onClick={() => setConfirmDelete(t.id)}>Delete</PixelButton>
// ...
{confirmDelete && (
  <ConfirmModal
    title="Delete Template?"
    message="This cannot be undone."
    variant="danger"
    onConfirm={() => { handleDelete(confirmDelete); setConfirmDelete(null); }}
    onCancel={() => setConfirmDelete(null)}
  />
)}
```

### 2. No loading/disabled state during activate and delete
**Severity:** medium
**Lines:** 205-213, 786-792

When clicking "Activate" or "Delete", there's no visual feedback (no spinner, no disabled state). Users can click multiple times, triggering duplicate API calls.

**Suggested Fix:** Add an `actionBusy` state:
```tsx
const [actionBusy, setActionBusy] = useState<string | null>(null);
// In handleActivate: setActionBusy(id); try {...} finally { setActionBusy(null); }
// In render: disabled={actionBusy === t.id}
```

### 3. Activate/delete errors not shown in list view
**Severity:** medium
**Lines:** 196, 205-213

The `error` state is only rendered in the editor view (line 450). The list view has no error display area, so if `handleActivate` or `handleDelete` were to set `error`, the user still wouldn't see it (and currently they don't even set it — see State Issue #1).

**Suggested Fix:** Add an error banner to the list view, similar to the editor view. Or use a toast notification pattern.

### 4. Editor and picker views don't use `ScreenContainer`
**Severity:** low
**Lines:** 389-433, 438-735

Only the list view (line 740) wraps in `<ScreenContainer>`. The editor and picker views return raw `<div>` elements, which may have different padding/scroll behavior.

**Suggested Fix:** Wrap all three views in `<ScreenContainer>` for consistent layout.
