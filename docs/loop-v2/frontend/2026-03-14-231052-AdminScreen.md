# Frontend Audit: AdminScreen

**Component Audited:** `apps/web/src/components/screens/AdminScreen.tsx` (704 lines)
**Date:** 2026-03-14

> Note: This is an admin-only screen. Severity ratings are adjusted — accessibility and UX polish are less critical for internal tooling.

---

## Accessibility

### 1. Tab buttons lack ARIA tab roles
**Severity:** low
**Lines:** 683-693

No `role="tablist"`, `role="tab"`, or `aria-selected` on the admin tab buttons.

**Suggested Fix:** Wrap in `<div role="tablist">` and add `role="tab"` + `aria-selected` to each button.

### 2. Inputs lack associated labels
**Severity:** low
**Lines:** 96, 105, 114, 125, 134, 185, 278, 399, 606, 634

Multiple `<input>` elements have no `<label>` or `aria-label`. They rely on nearby `<h3>` headings for context, which isn't programmatically linked.

**Suggested Fix:** Add `aria-label` to each input:
```tsx
<input aria-label="Turns to grant" type="number" ... />
```

### 3. Clickable list items not keyboard accessible
**Severity:** low
**Lines:** 251-261, 586-597

Item template and resource node selection use `<div onClick>` with no `role="option"` or `tabIndex`. Keyboard users can't navigate the lists.

**Suggested Fix:** Use `<button>` elements instead of `<div onClick>`, or add `role="option"` + `tabIndex={0}` + keyboard handler. Low priority for admin tooling.

## Component Duplication

### 1. `adminGetZones()` fetched independently by 3 tabs
**Severity:** medium
**Lines:** 311-319 (WorldTab), 467-473 (ZonesTab), 552-558 (ResourcesTab)

Three sub-components independently fetch the zone list. Switching between tabs triggers redundant API calls.

**Suggested Fix:** Fetch zones once in `AdminScreen` and pass as a prop:
```tsx
const [zones, setZones] = useState<AdminZone[]>([]);
useEffect(() => { adminGetZones().then(r => { if (r.data) setZones(r.data.zones); }); }, []);
// ...
{tab === 'world' && <WorldTab zones={zones} onAction={onAction} />}
{tab === 'zones' && <ZonesTab zones={zones} onAction={onAction} />}
{tab === 'resources' && <ResourcesTab zones={zones} onAction={onAction} />}
```

### 2. Input + button admin action rows highly repetitive
**Severity:** medium
**Lines:** 95-99, 104-108, 113-119, 124-128, 133-139, 633-639

The pattern `<input type="number"> + <PixelButton>` is repeated ~10 times with identical styling and structure. Only the value, onChange handler, and button label differ.

**Suggested Fix:** Extract an `<AdminNumberAction>` component:
```tsx
function AdminNumberAction({ label, value, onChange, buttonLabel, onAction, busy, min, max }: {
  label: string; value: number; onChange: (n: number) => void;
  buttonLabel: string; onAction: () => void; busy: boolean;
  min?: number; max?: number;
}) { ... }
```
This would reduce PlayerTab by ~60 lines.

### 3. Skill name list hardcoded twice
**Severity:** low
**Lines:** 163-164, 179-180

The full 15-skill array is listed inline twice. Should be a constant.

**Suggested Fix:** Extract to a module-level constant:
```tsx
const ALL_SKILLS = ['melee', 'ranged', 'magic', 'mining', ...];
```

## State Issues

### 1. Redundant zone fetches across tabs
**Severity:** medium
**Lines:** 311, 468, 553

Same as Component Duplication #1 — this is also a state concern. Three independent `useState` + `useEffect` chains for the same data. If zones change (admin creates one), only the current tab's state updates.

**Suggested Fix:** Lift zone state to `AdminScreen` as described above.

## UX Issues

### 1. No loading state for initial data fetches in WorldTab
**Severity:** low
**Lines:** 308-326

Four API calls fire on mount (`getEventTemplates`, `getActiveEvents`, `getZones`, `getMobs`) with no loading indicator. Selects render empty briefly until data arrives.

**Suggested Fix:** Add a loading boolean and show a `<LoadingCard />` until all four complete. Low priority for admin tooling.

### 2. Status messages not auto-dismissed
**Severity:** low
**Lines:** 45-52, 56, 67

`StatusMsg` persists until the next action replaces it. A success message from 5 minutes ago still shows if no new action is taken. Not confusing in practice since the message is contextual.

**Suggested Fix:** Add a `setTimeout` in `useAdminAction` to auto-clear after 5 seconds:
```tsx
setMsg({ text: ..., ok: true });
setTimeout(() => setMsg(null), 5000);
```
