# Frontend Audit: game/page.tsx

**Component Audited:** `apps/web/src/app/game/page.tsx` (1,368 lines)
**Date:** 2026-03-14

---

## Accessibility

### 1. Crafting and Gathering skill tab buttons lack ARIA tab roles
**Severity:** medium
**Lines:** 763-777, 864-881

Both crafting and gathering skill selectors render horizontally scrolling `<button>` lists but have no `role="tablist"`, `role="tab"`, or `aria-selected` attributes. Screen readers cannot identify them as tab navigation.

**Suggested Fix:** Wrap each in `<div role="tablist">` and add `role="tab"` + `aria-selected={active === tab.id}` to each button. Alternatively, reuse the `<SubNav>` component which already exists and handles this pattern.

### 2. Error banner not announced to screen readers
**Severity:** medium
**Lines:** 1303-1322

The `actionError` div appears dynamically but has no `role="alert"` or `aria-live="assertive"`. Screen readers won't announce errors when they appear.

**Suggested Fix:** Add `role="alert"` to the error div:
```tsx
<div ref={errorRef} role="alert" className={...}>
```

### 3. Broken gear warning banner lacks alert semantics
**Severity:** low
**Lines:** 1201-1212

The "You have broken equipment!" banner is purely visual — no `role="alert"` for screen reader announcement.

**Suggested Fix:** Add `role="alert"` to the banner div.

### 4. Loading state lacks status role
**Severity:** low
**Lines:** 419-425

The initial "Loading..." screen has no `role="status"` or `aria-live="polite"`.

**Suggested Fix:** Add `role="status"` to the loading container.

## Component Duplication

### 1. Crafting/Gathering tab bars duplicate the same pattern
**Severity:** medium
**Lines:** 763-777, 864-881

Both render identical horizontal scrolling button lists with the same active/inactive styling, same class names, same structure. The only difference is the tab data and click handler.

**Suggested Fix:** Extract a `<SkillTabBar tabs={...} activeId={...} onSelect={...} />` component, or reuse the existing `<SubNav>` component (already imported and used for the main navigation tabs). SubNav already handles the same visual pattern.

### 2. Durability calculation repeated 3 times
**Severity:** medium
**Lines:** 561-567 (Inventory), 608-610 (Equipment), 632-635 (Forge)

The pattern `templateMax = item.template.maxDurability ?? 0; max = item.maxDurability ?? templateMax; cur = item.currentDurability ?? max` is repeated with minor variations across three screen render cases.

**Suggested Fix:** Extract a `computeDurability(item)` utility:
```ts
function computeDurability(item: { currentDurability: number | null; maxDurability: number | null; template: { maxDurability?: number } }) {
  const templateMax = item.template.maxDurability ?? 0;
  const max = item.maxDurability ?? templateMax;
  if (max <= 0) return null;
  return { current: item.currentDurability ?? max, max };
}
```

### 3. XP efficiency rate calculation repeated
**Severity:** low
**Lines:** 363, 374, 672, 781, 885

`Math.round(calculateEfficiency(s.dailyXpGained, s.skillType as SkillType) * 100)` appears 5 times with minor variations.

**Suggested Fix:** Extract a `getXpRate(dailyXpGained: number, skillType: string): number` helper in `@/lib/format` or similar.

## State Issues

### 1. `filter(Boolean) as any` bypasses type safety
**Severity:** low
**Lines:** 676

```tsx
.filter(Boolean) as any}
```

This `as any` cast suppresses type checking on the Skills component's `skills` prop. If a skill type is missing from `SKILL_META`, it silently disappears without error.

**Suggested Fix:** Use a proper type assertion: `.filter((s): s is NonNullable<typeof s> => Boolean(s))` or define the return type explicitly.

### 2. `mailRecipient` not cleared on bottom nav away
**Severity:** low
**Lines:** 391, 1081-1084, 1297

`mailRecipient` is set when clicking "Send Mail" from friends, and cleared when switching SubNav tabs away from mail. But navigating away via bottom nav (e.g., Home tab) doesn't clear it. If the user later returns to Social → Mail, the old recipient could pre-populate the compose form.

**Suggested Fix:** Clear `mailRecipient` in `handleNavigate` when leaving the social tab, or in a `useEffect` that watches `activeTab`.

## UX Issues

### 1. Error banner uses brittle string matching
**Severity:** low
**Lines:** 1307-1320

```tsx
actionError.includes('active expedition')
```

The error styling and "Go to Guild Expeditions" link depend on the error message containing a specific substring. If the API error message changes, this special handling silently breaks.

**Suggested Fix:** Use structured error codes instead of string matching. The API already returns `res.error.code` — propagate a code alongside the message string and check that instead:
```tsx
if (actionErrorCode === 'ACTIVE_EXPEDITION')
```

### 2. Massive `renderScreen` switch makes page hard to maintain
**Severity:** low
**Lines:** 433-1157

The `renderScreen` function is a 700-line switch statement with 20+ cases, some containing significant inline JSX and data transformation logic (e.g., inventory item mapping at lines 544-575). This makes the file hard to navigate and increases the blast radius of changes.

**Suggested Fix:** Move inline data transformations into dedicated `useMemo` hooks at the top of the component (e.g., `inventoryItems`, `equipmentSlots`, `forgeItems`). This reduces the switch cases to simple component renders and makes the transformations independently testable.
