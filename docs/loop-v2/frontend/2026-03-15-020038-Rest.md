## State Issues

### 1. `handleRest` and `handleRecover` lack try/catch for network errors
**Severity:** medium
**Lines:** 90-114, 116-138

Both handlers call API functions (`api.rest`, `api.recoverFromKnockout`) without try/catch. If the network fails, the error propagates unhandled and `setIsLoading(false)` at lines 113/137 never runs, leaving the button permanently in "Resting..."/"Recovering..." state.

**Suggested Fix:** Wrap both in try/catch/finally:
```tsx
const handleRest = async () => {
  if (!hpState) return;
  setIsLoading(true);
  setError(null);
  try {
    const result = await api.rest(turns);
    if (result.error) { setError(result.error.message); return; }
    if (result.data) {
      onTurnsUpdate(result.data.turns.currentTurns);
      const newHpState = { ...hpState, currentHp: result.data.currentHp, maxHp: result.data.maxHp };
      setHpState(newHpState);
      onHpUpdate(newHpState);
    }
  } catch (err: unknown) {
    setError(err instanceof Error ? err.message : 'Rest failed');
  } finally {
    setIsLoading(false);
  }
};
```
Same pattern for `handleRecover`.

### 2. Estimate effect doesn't handle API errors
**Severity:** low
**Lines:** 61-79

The debounced estimate fetch (`api.restEstimate(turns)`) has no error handling. If the API fails, the old estimate remains stale. Minor since the estimate is informational only.

**Suggested Fix:** Add a catch block that clears the estimate on failure:
```tsx
try {
  const result = await api.restEstimate(turns);
  // ...existing logic...
} catch {
  setEstimate(null);
}
```

## UX Issues

### 1. Hardcoded recovery HP percentage
**Severity:** low
**Lines:** 175

```tsx
{Math.floor(hpState.maxHp * 0.25)} / {hpState.maxHp}
```

The "HP After Recovery" display hardcodes 25% (`* 0.25`). If the recovery HP constant changes on the backend, this UI value becomes wrong.

**Suggested Fix:** Import from shared constants if available, or show the value from the API response rather than computing it client-side.
