## State Issues

### 1. Combat log fetch has no staleness guard
**Severity:** medium
**Lines:** 94-114

When `combatEvent` changes, a new combat log fetch fires via `combatLogPrefetch.fetchLog(logId)`. If a first combat resolves quickly and a second combat starts before the first fetch completes, the first fetch's `.then()` could overwrite `loadedCombatLog` with stale data for the wrong fight.

**Suggested Fix:** Track a request generation counter or check currency:
```tsx
useEffect(() => {
  if (!combatEvent) { setLoadedCombatLog(null); return; }
  if (combatEvent.details?.log) {
    setLoadedCombatLog(combatEvent.details.log as CombatLogEntryResponse[]);
    return;
  }
  const logId = combatEvent.details?.combatLogId as string | undefined;
  if (logId && combatLogPrefetch) {
    const cached = combatLogPrefetch.getLog(logId);
    if (cached) { setLoadedCombatLog(cached); return; }
    const expectedId = logId;
    void combatLogPrefetch.fetchLog(logId).then(log => {
      // Only set if still the same combat
      if (combatEvent?.details?.combatLogId === expectedId) {
        setLoadedCombatLog(log);
      }
    });
  }
}, [combatEvent, combatLogPrefetch]);
```

In practice this race is unlikely since combats are sequential, but the pattern is fragile.

## UX Issues

No issues found. The component handles the complex orchestration of exploration → combat → resume well:
- Keeps exploration mounted but hidden during combat to preserve scroll/progress state
- Pre-fetches the next ambush's combat log for seamless transitions
- Auto-skips known mob victories while still showing defeats
- Tracks player HP between sequential combats
- Supports both embedded (no wrapping card) and standalone modes
