# Security Fix Loop

Process the next security finding from the tracker, validate it, and implement the fix in an isolated worktree.

## Process

### Step 0: Fresh Context

Run `/clear` before starting. Each invocation must begin with zero prior context to avoid hallucinating state from a previous finding.

### Step 1: Find Next Finding

Read `docs/loop-security/tracker.md` and find the first row with status `TODO` (process in order: critical → medium → low).

If all items are `DONE`, `FALSE_POSITIVE`, or `SKIPPED` — output "All security findings processed!" and stop.

### Step 2: Read the Audit Details

Read the source audit file from `docs/loop-security/<source file>` referenced in the tracker row. Find the specific finding section that matches the tracker description. Note:
- The exact code file paths and line numbers
- The described vulnerability
- The suggested fix

### Step 3: Validate Against Current Code

Read the actual source files mentioned in the finding. Verify:
1. Does the vulnerability still exist in the current code?
2. Is the described exploit actually possible given the current implementation?
3. Are there existing guards the audit may have missed?

**If the finding is invalid** (already fixed, or the audit was wrong):
- Update the tracker row status to `FALSE_POSITIVE`
- Add a brief note in the Branch column explaining why
- Stop here — the next loop iteration will pick up the next finding

**If the finding is valid**, continue to Step 4.

### Step 4: Create Worktree & Implement Fix

1. Create an isolated worktree:
   ```bash
   ./scripts/setup-worktree.sh security/fix-<NUMBER>-<short-name> --no-seed
   ```
   Where `<NUMBER>` is the finding number (zero-padded, e.g., `01`) and `<short-name>` is a kebab-case summary (e.g., `jwt-fallback`, `loot-double-claim`).

2. Update tracker status to `IN_PROGRESS` and add the branch name.

3. Navigate to the worktree directory and implement the fix:
   - Follow the suggested fix from the audit as a starting point
   - Keep changes minimal and focused — only fix the specific vulnerability
   - Do NOT refactor surrounding code or add unrelated improvements
   - Add inline comments only where the security fix is non-obvious

4. If the fix requires a database migration, create it with:
   ```bash
   cd /d/Code/Adventure/.worktrees/security-fix-<NUMBER>-<short-name>
   npx prisma migrate dev --name security-fix-<NUMBER>-<short-description>
   ```

### Step 5: Verify

Run the following checks in the worktree:

```bash
cd /d/Code/Adventure/.worktrees/security-fix-<NUMBER>-<short-name>

# 1. Type check
npm run typecheck

# 2. Run tests related to the changed area
npm run test:engine   # if game-engine files changed
npm run test:api      # if API files changed

# 3. Build check
npm run build
```

**If tests fail:**
- Investigate and fix the test failures
- Re-run verification
- If you cannot resolve after 2 attempts, update tracker status to `SKIPPED` with a note and move on

### Step 6: Commit, PR & Update Tracker

1. Commit the changes in the worktree:
   ```bash
   cd /d/Code/Adventure/.worktrees/security-fix-<NUMBER>-<short-name>
   git add -A
   git commit -m "security: fix #<NUMBER> — <short description>"
   ```

2. Push the branch and create a PR:
   ```bash
   git push -u origin security/fix-<NUMBER>-<short-name>
   gh pr create --title "security: fix #<NUMBER> — <short description>" --body "$(cat <<'EOF'
   ## Security Fix #<NUMBER>

   **Finding:** <one-line description from tracker>
   **Severity:** <critical/medium/low>
   **Source audit:** `docs/loop-security/<source file>`

   ### Vulnerability
   <2-3 sentence explanation of what the vulnerability was and how it could be exploited>

   ### Fix
   <brief description of what was changed>

   ### Files Changed
   - `<file1>`
   - `<file2>`

   ### Verification
   - [ ] Typecheck passes
   - [ ] Tests pass
   - [ ] Build succeeds

   🔒 Generated by security-fix loop
   EOF
   )"
   ```

3. Update the tracker in the **main worktree** (`docs/loop-security/tracker.md`):
   - Change status to `DONE`
   - Add the branch name in the Branch column

4. Commit the tracker update in the main worktree:
   ```bash
   cd /d/Code/Adventure
   git add docs/loop-security/tracker.md
   git commit -m "docs: mark security finding #<NUMBER> as done"
   ```

### Step 7: Summary

Output a brief summary:
- Finding number and description
- What was changed (files modified)
- Test results (pass/fail)
- PR URL

## Rules

- Only process ONE finding per invocation
- Always validate before implementing — never blindly trust the audit
- Keep fixes minimal — security-only changes
- Always create a PR with a clear description of the vulnerability and fix
- If a finding requires changes across many files or is architecturally complex, mark it `SKIPPED` with a note explaining why it needs manual attention
- Always work in a worktree, never modify main directly (except tracker updates)
